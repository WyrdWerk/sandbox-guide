# Daytona: sandbox research

Disclosure: battleships.dev, cited in this document, is built by the Boat team; Boat is one of the providers compared here. It is used as a cross-check, never as the sole source of a rate or verdict.

Research date: 2026-10-28. Desk research only; no account, sandbox, purchase, or runtime test. Evidence tags describe the source, not independent verification. Each quoted excerpt below was checked against its linked live source; source content can change. `not-published` means not found in the sources inspected, not a definitive statement that the feature does not exist. `inferred` identifies reasoning and its evidence.

## 1. What it is

- **docs-confirmed** — "Daytona is a secure and elastic infrastructure for running AI-generated code." [Documentation](https://www.daytona.io/docs).
- **docs-confirmed** — The unit is a sandbox: "Each sandbox runs in isolation, giving it a dedicated kernel, filesystem, network stack, and allocated vCPU, RAM, and disk." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md). See §2: that sentence is contradicted two paragraphs later for the default class.
- **docs-confirmed** — "Sandboxes run as **Linux containers** by default." VM classes exist for "a dedicated [Linux VM](https://www.daytona.io/docs/en/linux-sandboxes.md) or [Windows](https://www.daytona.io/docs/en/windows-sandboxes.md) operating system", plus GPU and macOS. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Speed is the headline claim: "Sub 90ms sandbox creation from code to execution." [Homepage](https://www.daytona.io/). The same claim is repeated in the repo README and in the docs' container card ("`<90ms`") [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — This is infrastructure to build an agent around, not a turnkey agent product. Evidence: the five SDKs and CLI are the documented entry points [Architecture](https://www.daytona.io/docs/en/architecture.md), and the company's own AI position is "Daytona does not ship AI-assisted features inside the product" [Trust Center](https://trust.daytona.io/).

## 2. Isolation and privileges

- **docs-confirmed** — The isolation page distinguishes three runtime boundaries. Container: "Isolated container with dedicated namespaces and enforced resource limits. Code runs as root inside the sandbox without affecting the runner." VM: "Full virtual machine with its own kernel." GPU: "Isolated container with exclusive GPU allocation." [Isolation](https://www.daytona.io/docs/en/isolation.md).
- **inferred** — So "dedicated kernel" in §1 is true of Linux VM and Windows sandboxes only. A container sandbox shares the runner's kernel; that is what "dedicated namespaces" means.
- **docs-confirmed** — Resources are hard limits, not shares: "Each sandbox reserves its own **vCPU**, **memory**, and **disk**, enforced as hard limits, so one sandbox cannot consume the resources of another regardless of what its code does." [Isolation](https://www.daytona.io/docs/en/isolation.md).
- **docs-confirmed** — Limits are visible through cgroups, but common tools mislead: "Tools such as `nproc` and `free` read host-level values and do not reflect the sandbox's own limits." [Isolation](https://www.daytona.io/docs/en/isolation.md).
- **docs-confirmed** — Root inside the sandbox is normal for the container class; the isolation table's phrase is "Code runs as root inside the sandbox without affecting the runner." [Isolation](https://www.daytona.io/docs/en/isolation.md). The default OS user is `daytona`. [Warm pools](https://www.daytona.io/docs/en/warm-pools.md).
- **docs-confirmed** — Nested virtualisation exists only on Linux VM sandboxes and only when enabled: "Nested virtualization exposes KVM (`/dev/kvm`) inside the guest" and "KVM sandboxes must be enabled for your organization." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Docker-in-Docker is documented: "Sandboxes can run Docker containers inside them (**Docker-in-Docker**)" with pre-built `docker:28.3.3-dind` images. [Snapshots](https://www.daytona.io/docs/en/snapshots.md).
- **not-published** — A kernel-module, eBPF, or systemd compatibility matrix was not found in the docs inspected. A separate kernel on the VM classes does not imply arbitrary kernel configuration.

## 3. Lifecycle

- **docs-confirmed** — Lifecycle capability differs by class: pause/resume, fork and memory snapshots exist only on the VM classes (Linux VM and Windows); archive is container-only. The matrix reads "Pause / resume sandboxes | ✗ | ✓ | ✓ | ✗" and "Archive sandboxes | ✓ | ✗ | ✗ | ✗" across Container, Linux VM, Windows, GPU. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — "Daytona sandboxes are persistent by default. Stopping a sandbox does not destroy it" — filesystem, identity and configuration survive a stop. [Persistence](https://www.daytona.io/docs/en/persistence.md).
- **docs-confirmed** — Container stop keeps the filesystem but not memory: "Stopping terminates the running container. The filesystem is preserved, but memory state is not." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md). VM pause keeps both: "The filesystem and memory state are preserved, and CPU is no longer consumed." [same page](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Default idle timeout is 15 minutes for containers: "if not set, the default interval of 15 minutes is used", and "The auto-stop triggers even if there are internal processes running in the sandbox." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md). **Figure** — idle stop: 15 min (container/GPU), 60 min auto-pause (VM).
- **docs-confirmed** — Idle means external interaction only: the timer resets on lifecycle calls, preview requests, active SSH and Toolbox API calls; it does not reset for "Background scripts (e.g., `npm run dev` run as a fire-and-forget command)" or "Long-running tasks without external interaction". The page's own warning: "If you run a long-running task like LLM inference that takes more than 15 minutes to complete without any external interaction, the sandbox may auto-stop mid-process". [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Auto-pause is the VM default instead: "if neither auto-pause nor auto-stop is set, non-ephemeral sandbox classes that support pausing default to an auto-pause interval of 60 minutes with auto-stop disabled", and the two intervals are "mutually exclusive". [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Auto-archive applies to stopped containers: default 7 days, maximum 30, where "`0`: the maximum interval of 30 days is used". [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md). **Figure** — stopped-container retention: 7 days to archive by default.
- **docs-confirmed** — Nothing is deleted by default: "if not set, the sandbox is not deleted automatically", `0` deletes immediately on stop, `-1` disables deletion. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — A wall-clock TTL is optional and destroys the sandbox "in any state: started, stopped, paused, or archived"; it is off unless set. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Transitions bill as running: "Billed the same as started. Resources remain reserved during these transitions, so reduced billing applies once the sandbox reaches the stopped or paused state, not when the stop or pause operation begins." [Billing](https://www.daytona.io/docs/en/billing.md).
- **not-published** — Resume latency, wake-from-stop latency, and the duration of creating/stopping transitions are not published. "Sub 90ms" describes creation-to-execution, not resume; warm pools are described only as "available instantly" [Warm pools](https://www.daytona.io/docs/en/warm-pools.md). **Figure** — wake time: not published.

## 4. Snapshots, forks, templates and volumes

- **docs-confirmed** — Two snapshot kinds. Cold captures the filesystem and requires a stopped sandbox; hot captures "Filesystem and memory" and requires a started VM sandbox. Containers support cold only. [Snapshots](https://www.daytona.io/docs/en/snapshots.md).
- **docs-confirmed** — Snapshots go inactive rather than being deleted: "Snapshots automatically become inactive after 2 weeks of not being used." Reactivation is a separate call. [Snapshots](https://www.daytona.io/docs/en/snapshots.md). **Figure** — snapshot retention: inactive after 14 days unused; no deletion deadline published.
- **docs-confirmed** — Default snapshot quota is 30: "raises the default snapshot quota to 30" [Changelog v0.175.0](https://www.daytona.io/changelog), 12 May 2026. **Figure** — 30 snapshots per organization by default.
- **docs-confirmed** — Deleting a sandbox does not delete its snapshots, and they keep billing: "Snapshots created from sandbox remain billed for storage." [Billing](https://www.daytona.io/docs/en/billing.md); "deleting the sandbox does not delete snapshots created from it" [Persistence](https://www.daytona.io/docs/en/persistence.md).
- **docs-confirmed** — Fork is VM-only and clones memory plus filesystem: "Forking creates a duplicate of a Linux VM sandbox's filesystem and memory state in a new sandbox." Lineage is tracked, and "The parent sandbox cannot be deleted while it has active fork children." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **docs-confirmed** — Images: container and GPU sandboxes can be built from a Dockerfile or OCI image through the declarative builder; VM snapshots cannot. "VM snapshots (Linux VM and Windows) cannot be built from a Dockerfile." [Declarative Builder](https://www.daytona.io/docs/en/declarative-builder.md).
- **docs-confirmed** — Volumes are S3-backed FUSE mounts, shareable across sandboxes, and free: "Daytona volumes are included at no additional cost. Each organization can create up to 100 volumes, and volume data does not count against your storage quota." [Volumes](https://www.daytona.io/docs/en/volumes.md). **Figure** — 100 volumes per organization, $0.
- **docs-confirmed** — They are not a database disk: "Since volumes are FUSE-based mounts, they can not be used for applications that require block storage access (like database tables)." [Volumes](https://www.daytona.io/docs/en/volumes.md).
- **docs-confirmed** — Warm pools pre-create running sandboxes from a snapshot, but are gated: "Warm pools must be enabled for your organization." [Warm pools](https://www.daytona.io/docs/en/warm-pools.md).
- **inferred** — A warm sandbox is a running sandbox, so it bills at the running rate while it waits. The docs say warm sandboxes "count against your organization quota in the same way as regular sandboxes" but do not state idle-pool billing [Warm pools](https://www.daytona.io/docs/en/warm-pools.md); treat pool cost as running cost until Daytona says otherwise.

## 5. Sizes, GPU, architecture and regions

- **docs-confirmed** — Default shape is small: "Sandboxes have **1 vCPU**, **1GB RAM**, and **3GiB disk** by default. Organizations get a maximum sandbox resource limit of **4 vCPUs**, **8GB RAM**, and **10GB disk**." [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md). **Figure** — per-sandbox ceiling: 4 vCPU / 8 GiB / 10 GiB.
- **docs-confirmed** — Named presets: `daytona-small` 1/1/3, `daytona-medium` 2/4/8, `daytona-large` 4/8/10; Linux VM equivalents `daytona-vm-small/medium/large` at the same shapes; Windows `windows-small` 1/4/30, `windows-medium` 2/8/50, `windows-large` 4/16/50. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — The 10 GiB disk ceiling and the 30/50 GiB Windows presets cannot both be the per-sandbox maximum. The ceiling is stated as an organization default ("Organizations get a maximum…") and the limits page offers a Custom tier whose resources and access requirement are both "Custom", routed to support [Limits](https://www.daytona.io/docs/en/limits.md), so a 50 GiB Linux sandbox needs a raised limit that has no published price or approval path beyond support.
- **docs-confirmed** — GPU sandboxes attach "up to **8 GPUs**" and "each GPU adds up to **16 vCPUs**, **192GB RAM**, and **512GB disk**", across H100, H200, B200, B300, RTX PRO 6000, RTX 4090, RTX 5090 and AMD MI355X. [GPU sandboxes](https://www.daytona.io/docs/en/gpu-sandboxes.md).
- **docs-confirmed** — Two shared regions only: "United States | **`us`**" and "Europe | **`eu`**". [Regions](https://www.daytona.io/docs/en/regions.md). **Figure** — 2 shared regions.
- **docs-confirmed** — GPU on shared capacity ignores your choice of region: "Daytona selects the shared region a GPU workload runs in and ignores the region preference", reporting it as the reserved `earth` region. [Regions](https://www.daytona.io/docs/en/regions.md).
- **docs-confirmed** — Dedicated regions (Daytona-operated, single-tenant) and custom regions (your own runners, BYOC) exist; BYOC "must be enabled for your organization". [Regions](https://www.daytona.io/docs/en/regions.md), [BYOC](https://www.daytona.io/docs/en/bring-your-own-compute.md).
- **docs-confirmed** — macOS is a separate platform in the current docs: "macOS sandboxes are provided through the [use.computer ↗](https://use.computer) platform" and "The Daytona SDKs, CLI, and API do not manage macOS sandboxes." [macOS sandboxes](https://www.daytona.io/docs/en/macos-sandboxes.md).
- **docs-confirmed** — The alpha v2 docs describe the opposite arrangement — Daytona-managed Mac reservations at "**$2.5032 per Mac-hour, $60.08 per 24-hour period**" for an `m4pro-12c-24g` with 12 cores, 24 GiB and 220 GiB disk. [v2 macOS sandboxes](https://www.daytona.io/docs/en/v2/macos-sandboxes/). **Figure** — macOS: $60.08 per Mac-day (alpha docs only).
- **not-published** — Guest CPU architecture is not stated for Linux, Windows or GPU sandboxes; no arm64 option is documented. macOS runs on Apple silicon, which is a different product surface.

## 6. Networking and secrets

- **docs-confirmed** — Outbound access is tier-gated, not neutral: "**Tier 1 & Tier 2**: Network access is restricted and cannot be overridden at the sandbox level." "**Tier 3 & Tier 4**: Full internet access is available by default". [Network limits](https://www.daytona.io/docs/en/network-limits.md). **Figure** — full outbound internet: Tier 3, a $500 top-up.
- **docs-confirmed** — Per-sandbox controls are block-all, CIDR allow list, domain allow list or an upstream proxy; the three list options are "mutually exclusive". On Tier 3/4 "Essential services do not bypass a sandbox allow list or block-all setting." [Network limits](https://www.daytona.io/docs/en/network-limits.md).
- **docs-confirmed** — Inbound is through an authenticated proxy: `https://{port}-{sandboxId}.{proxy-domain}`, "If a sandbox has its `public` property set to `true`, preview links are publicly accessible without authentication. Otherwise, authentication is required." [Preview](https://www.daytona.io/docs/en/preview.md).
- **docs-confirmed** — The standard preview token is a sandbox-wide credential: "The token returned by `get_preview_link()` is not restricted to the port you requested it for… Anyone holding it can run commands in the sandbox and read or write its filesystem", and "there is no way to revoke a standard preview token". [Preview](https://www.daytona.io/docs/en/preview.md).
- **docs-confirmed** — Signed preview URLs are the shareable form, "bound to one port, expires, and can be revoked", with default 60 seconds and maximum "`86,400` seconds (24 hours)". [Preview](https://www.daytona.io/docs/en/preview.md). **Figure** — signed link: 60 s default, 24 h maximum.
- **docs-confirmed** — SSH is token-based with a 60-minute default expiry: "SSH access tokens expire automatically after 60 minutes." [SSH access](https://www.daytona.io/docs/en/ssh-access.md). **Figure** — SSH token: 60 min.
- **docs-confirmed** — Secrets never enter the sandbox in plaintext: an opaque `dtn_secret_…` placeholder is swapped by an outbound proxy, and "The proxy substitutes placeholders in HTTPS request headers only." [Secrets](https://www.daytona.io/docs/en/secrets.md).
- **docs-confirmed** — Consequences: "If a service only accepts credentials in the body or query string, secrets cannot authenticate to it", and "A secret without an allowlist is substituted for every host." [Secrets](https://www.daytona.io/docs/en/secrets.md).
- **docs-confirmed** — No native custom domain: the documented route is your own proxy — "Daytona provides a preview proxy service that can be used to handle preview URLs for sandboxes… **Custom domain**: host your proxy under your own domain". [Custom preview proxy](https://www.daytona.io/docs/en/custom-preview-proxy.md). **Figure** — custom domains: none native.
- **docs-confirmed** — VPN into private networks (Tailscale, OpenVPN, Netbird) requires Tier 3 or higher: you need "access to your VPN network provider credentials, and be on [**Tier 3** or higher](https://www.daytona.io/docs/en/limits.md#resources)". [VPN connections](https://www.daytona.io/docs/en/vpn-connections.md).
- **not-published** — No static or dedicated egress IP is documented anywhere in the docs corpus, pricing page or FAQ; egress bytes are not on the price card either. **Figure** — static egress IP: not published.

## 7. Interfaces

- **docs-confirmed** — Five SDKs plus CLI, dashboard, MCP and SSH: "Python, TypeScript, Ruby, Go, and Java SDKs for programmatic access". [Architecture](https://www.daytona.io/docs/en/architecture.md).
- **docs-confirmed** — The API is REST: "The API is a NestJS-based RESTful service that serves as the primary entry point for all platform operations". [Architecture](https://www.daytona.io/docs/en/architecture.md).
- **docs-confirmed** — MCP server is a first-party CLI subcommand: "`daytona mcp init claude`", with tools for sandbox management, files, git, execution, computer use and previews. [MCP](https://www.daytona.io/docs/en/mcp.md).
- **docs-confirmed** — Webhooks exist but are gated: "contact [support@daytona.io](mailto:support@daytona.io) to enable webhooks for your organization" [Webhooks](https://www.daytona.io/docs/en/webhooks.md).
- **docs-confirmed** — Browser access is built in: a web terminal ("full terminal session connected to your sandbox") [Web terminal](https://www.daytona.io/docs/en/web-terminal.md) and VNC desktop [Computer Use](https://www.daytona.io/docs/en/computer-use.md).
- **docs-confirmed** — An agent skill is published for driving the platform: "An agent skill for creating and running sandboxes on the Daytona platform." [Agent skills](https://www.daytona.io/docs/en/agent-skills.md).
- **not-published** — A supported-language matrix for the Toolbox API inside the sandbox (beyond the SDKs) was not established.

## 8. Agent features

- **docs-confirmed** — Computer use is a first-class API: "Computer Use enables programmatic control of desktop environments within sandboxes. It provides mouse, keyboard, screenshot, screen recording, and display operations". [Computer Use](https://www.daytona.io/docs/en/computer-use.md).
- **docs-confirmed** — Coding-agent guides are first-party and numerous: Claude Code, Codex, Cursor, Devin, Gemini CLI, OpenCode, Amp, Kiro and others. [Guides index](https://www.daytona.io/docs/en/guides.md); example: "Run Claude Code in a Daytona Sandbox via CLI" [Claude guide](https://www.daytona.io/docs/en/guides/claude/claude-code-run-cli-sandbox.md).
- **docs-confirmed** — The company's own framing of the buyer: "AI models, agents, and human developers to execute code, run software, and store data in isolated sandboxes". [Terms](https://www.daytona.io/terms-of-service).
- **inferred** — Daytona supplies the computer and the control API, not the agent. There is no hosted agent runtime, model, or per-task agent product in the docs; the trust centre states "Daytona does not ship AI-assisted features inside the product". [Trust Center](https://trust.daytona.io/).
- **not-published** — No published agent-harness abstraction (task queue, agent loop, evaluation harness) beyond SDK examples and the RL cookbook guides.

## 9. Accounts and governance

- **docs-confirmed** — Two organization types: "Every Daytona user starts with a personal organization" and collaborative organizations add "Roles with granular resource-based assignments". [Organizations](https://www.daytona.io/docs/en/organizations.md).
- **docs-confirmed** — The organization, not the role, is the sandbox boundary: "Every member of an organization can address that organization's running sandboxes — running processes, reading and writing files, opening preview URLs and using the web terminal and the Computer Use desktop — whatever assignments they hold, including none." [Organizations](https://www.daytona.io/docs/en/organizations.md).
- **docs-confirmed** — API keys repeat the same rule: "Sandbox runtime access is not a grantable scope. Any API key valid for an organization can address that organization's running sandboxes through the toolbox". [API keys](https://www.daytona.io/docs/en/api-keys.md).
- **docs-confirmed** — A `write:sandboxes` key can also reach secrets and schedules: it "can mount any secret in the organization without holding `manage:secrets`", and setting auto-delete or TTL needs only `write:sandboxes`. [API keys](https://www.daytona.io/docs/en/api-keys.md).
- **docs-confirmed** — SSO is Enterprise-only: "SSO is available on the Enterprise plan for collaborative organizations. Personal organizations cannot configure SSO." [SSO](https://www.daytona.io/docs/en/sso.md).
- **docs-confirmed** — Audit logs are role-gated, and export is not shipped: "**Compliance Export**: export logs for internal or external audits (coming soon)". [Audit logs](https://www.daytona.io/docs/en/audit-logs.md).
- **not-published** — Audit-log retention, a log export format, SCIM provisioning detail, and per-key IP restrictions were not established. The pricing page lists "SSO, audit logs" under Enterprise [Pricing](https://www.daytona.io/pricing) while the audit-log doc gates them by permission rather than plan — see §14.

## 10. Pricing and limits

- **pricing-page** — Four non-GPU meters and no plan fee: "vCPU $0.0504/h", "Memory GiB $0.0162/h", "Storage GiB $0.000108/h" with the footnote "* Price per GiB after first 5 free", and "OS Windows $0.0858/vCPU/h". [Pricing](https://www.daytona.io/pricing).
- **pricing-page** — "All billing is calculated per second." [Pricing](https://www.daytona.io/pricing). **docs-confirmed** — Billing is on reservation, not use: "Sandboxes are billed for the resources reserved: **vCPU**, **RAM**, and **disk**". [Billing](https://www.daytona.io/docs/en/billing.md).
- **docs-confirmed** — State table: Started bills all three; Stopped and Paused bill "reserved disk only" and "The preserved memory state is not billed"; Archived and Deleted bill nothing. [Billing](https://www.daytona.io/docs/en/billing.md). **Figure** — price while paused: disk only, $0.000108/GiB-hour.
- **pricing-page** — Free allowance: "$200 in free compute included" and "Sign up for a free trial - no credit card required". [Pricing](https://www.daytona.io/pricing). **docs-confirmed** — It is not universal: "**Free credit balance**: the amount of free credits; not available for GPU sandboxes". [Billing](https://www.daytona.io/docs/en/billing.md). **Figure** — $200 free credit, GPU-excluded.
- **docs-confirmed** — Tiers are prepaid top-ups that set an org-wide pool: Tier 1 "10 / 10GiB / 30GiB" on email verification; Tier 2 "100 / 200GiB / 300GiB" at "Credit card linked, $25 top-up"; Tier 3 "250 / 500GiB / 2000GiB" at "$500 top-up"; Tier 4 "500 / 1000GiB / 5000GiB" at "$2000 top-up every 30 days". [Limits](https://www.daytona.io/docs/en/limits.md). **Figure** — $25 / $500 / $2,000-per-30-days.
- **docs-confirmed** — Creation rate limits rise with tier: 300, 400, 500 and 600 sandbox creations per minute. [Limits](https://www.daytona.io/docs/en/limits.md). **Figure** — 300 creates/min at Tier 1.
- **docs-confirmed** — Volume discounts are not published: the pricing page says only "Unlock volume discounts as you scale". [Pricing](https://www.daytona.io/pricing).
- **pricing-page** — Startup credits: "Daytona supports startups with up to **$50k in credits for free**." [Pricing](https://www.daytona.io/pricing). **docs-confirmed** — The startups page says "Get up to $100k in Daytona credits for your startup" and "$10K straight away". [Startups](https://www.daytona.io/startups). Contradiction; see §14.
- **inferred** — Windows pricing is ambiguous: "$0.0858/vCPU/h" sits in a separate "OS" row, which reads either as a replacement for $0.0504 or as a surcharge on top. No page resolves it; both readings are priced in §11.
- **not-published** — Whether snapshot storage is charged at the $0.000108/GiB-hour storage meter (billing only says snapshots "remain billed for storage"), egress/ingress bytes, GPU vCPU/RAM composition, per-sandbox limit-increase prices, dedicated-region and BYOC prices, minimum billed seconds beyond "per second", and credit expiry were not published in the sources inspected. Do not treat an omitted price as zero.

## 11. Worked examples

All figures are **inferred** from the [published rate card](https://www.daytona.io/pricing) and [billing rules](https://www.daytona.io/docs/en/billing.md); they exclude taxes, model/API costs, snapshot storage, egress and transition time. 2 vCPU/4 GiB = $0.1656/hour; 4 vCPU/8 GiB = $0.3312/hour; disk $0.000108/GiB-hour. The "first 5 free" storage allowance is applied per sandbox where shown; its scope (per sandbox or per organization) is not stated. Where a workload asks for more disk than the published 10 GiB per-sandbox cap, both the theoretical figure and the nearest published shape are given — treating 10 GiB as the real cap is a judgement call, because the 30/50 GiB Windows presets contradict it (see §5 and §14).

- **inferred** — **A: 1,000 × ten-minute tasks, 2 vCPU / 4 GiB, deleted after each.** 166.67 running hours × $0.1656 = **$27.60 compute**; 8 GiB disk for 166.67 h = $0.14, or $0.05 with the 5 GiB allowance. **≈ $27.74**, no idle tail because each sandbox is deleted. `daytona-medium` is exactly this shape. Tier 1's 10 vCPU pool allows five concurrent sandboxes (fewer if the 10 GiB RAM reading of Tier 1 applies), and its restricted egress may break package installs that Tier 1's essential-services list does not cover.
- **inferred** — **B: one always-on 4 vCPU / 8 GiB / 50 GiB box for 730 hours.** 730 × $0.3312 = **$241.78 compute** + 50 GiB × 730 h = **$3.94 disk** → **$245.72** *if Daytona sold that shape*. It does not: 50 GiB exceeds the published 10 GiB per-sandbox disk cap for container and Linux VM classes. The nearest published shape is `windows-large` (4 vCPU / 16 GiB / 50 GiB) at 4 × $0.0858 + 16 × $0.0162 = $0.6024/h → **$443.69** for the month (replacement reading), or **$590.86** if the Windows rate is additive. 50 GiB also exceeds Tier 1's 30 GiB storage pool, so Tier 2 ($25 top-up) is the minimum.
- **inferred** — **C: one 2 vCPU / 4 GiB / 20 GiB box, 3 h/day for 30 days, stopped otherwise.** 90 running hours × $0.1656 = **$14.90 compute**; 20 GiB × 720 h = **$1.56 disk** (running and stopped alike) → **$16.46**, again *if the 20 GiB disk were available*. The published 2/4 shape is `daytona-medium` with 8 GiB: 90 × $0.1656 + 8 × 720 × $0.000108 = **$15.53**. Paused time is not applicable — containers cannot pause; stop is disk-only.

## 12. Same word, different meaning

- **inferred** — "Stop" is not "delete", and for containers it is not "pause". Stop keeps the filesystem, clears memory and keeps billing disk; delete is terminal; pause exists only on VM classes. Evidence: [billing](https://www.daytona.io/docs/en/billing.md), [sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — "Snapshot" means two different things: a cold filesystem capture from a stopped sandbox, or a hot filesystem-plus-memory capture from a started VM. A container "snapshot" can never include memory. Evidence: [snapshots](https://www.daytona.io/docs/en/snapshots.md).
- **inferred** — "Fork" is a VM-only memory clone; on containers the documented substitute is snapshot-then-create, which loses memory. Evidence: [sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — "Wake" is not request-driven. Nothing starts a stopped or paused sandbox on inbound traffic; you call start, or your own proxy does. Evidence: [preview](https://www.daytona.io/docs/en/preview.md) (no auto-start), [custom proxy](https://www.daytona.io/docs/en/custom-preview-proxy.md) ("automatically start stopped sandboxes before forwarding users").
- **inferred** — "Restricted network" on Tier 1/2 is an organization policy you cannot override per sandbox, not a sandbox setting you chose. Evidence: [network limits](https://www.daytona.io/docs/en/network-limits.md).
- **inferred** — "Unlimited persistence" in the marketing sense still meets a 14-day snapshot inactivity clock and a 7-day stopped-container archive clock. Evidence: [snapshots](https://www.daytona.io/docs/en/snapshots.md), [sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — "Sandbox limit" is a resource pool (vCPU/GiB), not a count of sandboxes. Evidence: [limits](https://www.daytona.io/docs/en/limits.md).

## 13. Glossary candidates

- **inferred** — Sandbox class: container, Linux VM, Windows, GPU or macOS; it decides which lifecycle features exist. Evidence: [isolation](https://www.daytona.io/docs/en/isolation.md).
- **inferred** — Cold snapshot: filesystem-only capture from a stopped sandbox. Evidence: [snapshots](https://www.daytona.io/docs/en/snapshots.md).
- **inferred** — Hot snapshot: filesystem plus memory from a started VM sandbox. Evidence: [snapshots](https://www.daytona.io/docs/en/snapshots.md).
- **inferred** — Warm pool: pre-created running sandboxes held ready for matching creates. Evidence: [warm pools](https://www.daytona.io/docs/en/warm-pools.md).
- **inferred** — Reserved resources: the allocation you pay for, whether or not the code uses it. Evidence: [billing](https://www.daytona.io/docs/en/billing.md).
- **inferred** — Ephemeral sandbox: one deleted on stop (`auto-delete` 0). Evidence: [sandboxes](https://www.daytona.io/docs/en/sandboxes.md).
- **inferred** — Earth region: the synthetic region ID under which shared GPU capacity is reported. Evidence: [regions](https://www.daytona.io/docs/en/regions.md).
- **inferred** — Secret placeholder: the `dtn_secret_…` token that stands in for a credential inside the sandbox. Evidence: [secrets](https://www.daytona.io/docs/en/secrets.md).

### Operational gotchas

1. **The idle timer ignores your workload.** A 40-minute compile or inference run with no inbound request or Toolbox call is stopped at minute 15 on a container. [Sandboxes](https://www.daytona.io/docs/en/sandboxes.md) · `docs-confirmed`.
2. **Stopping is not free.** Disk bills in stopped and paused states at $0.000108/GiB-hour; only archive (containers) and delete reach zero. [Billing](https://www.daytona.io/docs/en/billing.md) · `docs-confirmed`.
3. **Snapshots outlive the sandbox and keep billing.** Deleting a sandbox leaves its snapshots, and "Snapshots created from sandbox remain billed for storage." [Billing](https://www.daytona.io/docs/en/billing.md) · `docs-confirmed`.
4. **Tier 1 and 2 are network-restricted by default.** Package installs reach allowlisted "essential services" only, and you cannot override it per sandbox. Full internet needs a $500 top-up. [Network limits](https://www.daytona.io/docs/en/network-limits.md) · `docs-confirmed`.
5. **Prepaid top-ups are the tier gate.** Tier 4 requires "$2000 top-up every 30 days" — a de facto recurring spend, not a one-off. [Limits](https://www.daytona.io/docs/en/limits.md) · `docs-confirmed`.
6. **The standard preview token is a sandbox credential.** It opens the web terminal on 22222 and the toolbox on 2280, and cannot be revoked. [Preview](https://www.daytona.io/docs/en/preview.md) · `docs-confirmed`.
7. **Secrets only work in headers.** Basic Auth helpers that Base64-encode the placeholder, JSON bodies and query strings all fail. [Secrets](https://www.daytona.io/docs/en/secrets.md) · `docs-confirmed`.
8. **GPU sandboxes vanish on stop**, and spot GPUs can be killed "at any time without notice" with no preemption webhook. [GPU sandboxes](https://www.daytona.io/docs/en/gpu-sandboxes.md) · `docs-confirmed`.
9. **Roles do not protect running sandboxes.** Any member, and any org API key, can exec in any running sandbox. [Organizations](https://www.daytona.io/docs/en/organizations.md) · `docs-confirmed`.
10. **Webhooks, warm pools, BYOC and KVM each need a support request**, so a self-serve evaluation will not show them. [Webhooks](https://www.daytona.io/docs/en/webhooks.md), [Warm pools](https://www.daytona.io/docs/en/warm-pools.md), [BYOC](https://www.daytona.io/docs/en/bring-your-own-compute.md) · `docs-confirmed`.
11. **The open-source repo is archived.** "This repository is no longer maintained… As of June 2026, Daytona's core development has moved to a private codebase." [GitHub README](https://github.com/daytonaio/daytona) · `third-party` (GitHub is not Daytona); the API reports `"archived": true` and 71,446 stars · `third-party`.
12. **Two doc trees.** A reader who lands on `/docs/en/v2/` gets alpha behaviour, different API hosts, and a different macOS model. [v2 docs](https://www.daytona.io/docs/en/v2/macos-sandboxes/) · `docs-confirmed`.
