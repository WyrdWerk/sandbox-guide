### 0.2 How to read the evidence

Every claim carries a line in this shape:

`↳ https://url — "verbatim quote" — confidence`

The quote is a contiguous fragment of the cited page, checked mechanically after normalising: whitespace collapsed, HTML tags removed, and Markdown emphasis/backticks/pipes stripped. Nothing else was changed. If a quote needed more than that normalisation to match, it is flagged in the line. Confidence tags are the site's: `docs-confirmed`, `pricing-page`, `third-party`, `inferred`, `not-published`.

`not-published` means "searched the 2.0 docs, pricing, changelog, trust centre, status page and the 1.x pages on 2026-11-12 and did not find it". It is not a claim that the thing cannot exist.

### 0.3 The correction: $0.0706 is the *preemptible* column, not the price

The earlier 2.0 extraction in this thread's parent (its §3.2 and §7) read the first number in each pricing row as the rate. The live page's column order is **Preemptible | On demand**, and it opens on the Preemptible tab. The on-demand column is the list price a normal sandbox pays:

- `↳ https://www.daytona.com/pricing.md — "| Item | Preemptible | On demand |" — pricing-page`
- `↳ https://www.daytona.com/pricing.md — "| AMD Zen 3 · Intel Ice Lake · AWS Graviton 4 · Apple M4 | $0.0706 | $0.101 |" — pricing-page`
- `↳ https://www.daytona.com/pricing.md — "| RAM | $0.0113 | $0.0162 |" — pricing-page`
- `↳ https://www.daytona.com/docs/preemption.md — "Spot multiplies the CPU, memory, and disk price by 0.7" — docs-confirmed`
- `↳ https://www.daytona.com/docs/linux-sandboxes.md — "Runs the sandbox on discounted capacity that can be reclaimed. The default is `False`." — docs-confirmed`

Arithmetic: `$0.101 × 0.7 = $0.0707` and `$0.0162 × 0.7 = $0.01134`, i.e. the preemptible column is the on-demand column at 30% off, rounded to four significant figures. A default sandbox is on-demand, so **the base rate is $0.101 per core-hour and $0.0162 per GiB-hour**, and spot is the option.

That also settles the "2.0 is 30% cheaper" reading: it is not. The 1.x card was $0.0504 per **vCPU**-hour, and 2.0 charges $0.101 per **core**-hour where a core is 2 vCPUs — `$0.0505` per vCPU, within 0.2% of 1.x. 1.x memory was `$0.0162`/GiB-hour; 2.0 on-demand is `$0.0162`. 1.x Windows was `$0.0858`/vCPU-hour; 2.0 on-demand is `$0.172`/core-hour = `$0.086`/vCPU. **The on-demand price list is 1.x unchanged, re-expressed per core; the 30% saving is the spot tier.** The parent's totals built on $0.0706/$0.0113 are therefore spot totals, not list totals.

The two checks that make this airtight:

`↳ https://www.daytona.com/pricing.md — "One core is equivalent to 2 vCPUs where SMT (simultaneous multithreading, also called hyperthreading) is available and enabled, and 1 vCPU otherwise." — pricing-page`

`↳ https://www.daytona.io/pricing — "Compute vCPU $0.0504/h Memory GiB $0.0162/h Storage GiB $0.000108/h" — pricing-page`

(0.101 ÷ 2 = 0.0505; 0.172 ÷ 2 = 0.086. The 1.x page is still live and is the cheapest way to see the continuity.)

### 0.4 Bottom line

- **2.0 is a different product, not a version bump.** Every sandbox is a VM (Firecracker / Cloud Hypervisor / Apple Virtualization), sized freely from 0.125 to 16 cores, priced per core-second with a guaranteed floor, organised into organisations → projects, and sold as Starter / Team / Enterprise with macOS reservations, volumes, custom domains and static IPs as separate objects. `isolation` moves **partly → yes**.
- **The headline regression is lifecycle.** A Linux sandbox has no stop, no pause, no fork and no filesystem persistence: it runs until a 24-hour (Starter) or 48-hour (Team) timeout deletes it, and keeping files between sessions means a volume. That alone flips `stay-on`, `files-survive-stop`, `cheap-pause` and `fork-running`; the wider sandbox model also flips `live-resize`, `auto-https`, `backups` and `schedules`.
- **The headline price fact is that 2.0 did not cut prices.** On-demand CPU/memory/Windows are 1.x's rates relabelled per core. Only GPUs rose (B300 $6.25 → $8.99 on demand) and the 5 GiB free disk allowance disappeared. Spot is 30% off and is what the pricing page shows first.
- **A/B/C on Starter, on-demand, base region:** **A $27.63**, **B $246.01**, **C $16.50** (spot: $19.34 / $172.21 / $11.55). Starter wins all three; Team is never cheaper because its $100 monthly credit is $150 less than its $250 fee.
- **No EU region is documented.** The 2.0 region tree is Earth → United States → US East → Ashburn / Boston, plus `macos-1` for Macs. 1.x documented `us` and `eu`. `eu-region` therefore becomes `not-published` and the `eu-residency` situation should drop Daytona until confirmed.
- **GPU and Windows are stubs.** Their 2.0 pages are a paragraph plus "coming soon", while the price list already sells GPU cards, Windows core licences and nine GPU models. `gpu` becomes `partly`.
- **2.0 is alpha software.** The 1.x docs version switcher labels it **v2.0 Alpha** while **v0.231** is **Latest**; the CLI ships as `2.0.0-alpha.N`, the Python SDK as `2.0.0a10`, the TypeScript SDK as `2.0.0-alpha.10`. 1.x is still sold, still documented, still updated, and still supported through `daytona.v0` in the same SDK. No dated retirement statement exists.
- **Net verdict movement:** 2 of 16 features change verdict (isolation and reaching-it, both **partly → yes**); teams-accounts stays `partly` but its figure and catch change (it is a much better product with the same Enterprise gate). 21 of 78 capabilities change verdict (11 up, 8 down, 2 sideways to `not-published`). Full list in §1.2 and §2.1.

### 1.2 Feature detail

#### 1. isolation — **yes** (1.x: partly)

- **Figure:** `microVM, own kernel`
- **Scenario:** Docker runs because the image ships the engine, and `modprobe` works because every sandbox is its own Firecracker VM with its own kernel, not a namespace on a shared host.
- **Note:** Every sandbox is a VM: Linux on Firecracker, Windows and GPU on Cloud Hypervisor, macOS on Apple's Virtualization framework. The hypervisor, not the guest, draws the boundary, and the guest sees only its own vCPU, memory and disk. Docker is not installed by Daytona, so it works only when the image ships it. Nested virtualisation (`/dev/kvm`) is Enterprise-only. `nproc` inside reports the burst limit, not the guarantee, so size tooling by the guarantee.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/sandboxes.md — "A sandbox is a hardware-isolated virtual machine with its own kernel, filesystem, network stack, and allocated vCPU, RAM, and disk, with isolation enforced by the hypervisor." — docs-confirmed
  - ↳ https://www.daytona.com/docs/isolation.md — "Linux sandboxes on Firecracker, Windows and GPU sandboxes on Cloud Hypervisor, and macOS sandboxes on Apple's Virtualization framework" — docs-confirmed
  - ↳ https://www.daytona.com/docs/isolation.md — "The boundary is enforced by the hypervisor, not by the guest: code inside a sandbox cannot observe or interfere with other sandboxes or the host." — docs-confirmed
  - ↳ https://www.daytona.com/docs/docker.md — "Daytona does not install Docker. When the sandbox image ships Docker Engine, the sandbox starts it automatically on every boot; when the image does not, nothing starts." — docs-confirmed
  - ↳ https://www.daytona.com/pricing.md — "KVM access (nested virtualization)" — pricing-page
- **Differs from 1.x:** 1.x was *containers by default* with Linux VM, Windows and GPU as separate classes (`partly`, "containers by default"). 2.0 is VM-only, so the default boundary is the strongest one the product sells. The Docker catch changes from "container image, daemon present" to "your image must ship the engine"; the kernel-module catch disappears; the nested-virt catch becomes plan-gated (Enterprise).

#### 2. sizes-regions — **partly** (1.x: partly)

- **Figure:** `16 cores / 32 GiB (docs)`
- **Scenario:** A 16 GB agent fits on Team (8 cores / 32 GiB) but not on Starter (4 cores / 16 GiB), and the pricing page's 64 cores / 128 GiB describes a machine neither plan's own limits page allows.
- **Note:** Sizes are custom, not presets: 0.125–16 cores, 0.5–32 GiB memory and 10–256 GiB disk, with CPU raised to at least 1 core per 8 GiB of memory. The limits page caps Starter at 4 cores / 16 GiB and Team at 8 / 32; the pricing page's plan table says 64 cores / 128 GiB for both and 512 GiB–3 TiB disk (see §4.1). Regions are priced by multiplier: `earth` 1.0×, `us` 1.15×, `us-east` 1.75×, Ashburn and Boston 2.0×; macOS has its own `macos-1`. No EU region is documented.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/sandboxes.md — "A Linux sandbox may guarantee at most 16 cores, 32GiB memory, and 256GiB disk." — docs-confirmed
  - ↳ https://www.daytona.com/docs/limits.md — "Starter | 4 | 16384" — docs-confirmed
  - ↳ https://www.daytona.com/pricing.md — "| Cores | 64 | 64 | Custom |" — pricing-page
  - ↳ https://www.daytona.com/docs/regions.md — "Each region has its own price multiplier, applied to the base price of the sandbox's resources, and a region without one is billed at Earth's." — docs-confirmed
  - ↳ https://www.daytona.com/docs/regions — "United States us · 1.15× US East (Ashburn) us-east · 1.75× Ashburn us-east-ash-1 · 2.0× Boston us-east-bos-1 · 2.0×" — docs-confirmed
- **Differs from 1.x:** 1.x sold fixed presets to 4 vCPU / 8 GiB / 10 GiB in two shared regions (`us`, `eu`). 2.0 sells arbitrary sizes to 16 cores / 32 GiB / 256 GiB, adds plan caps and a region price multiplier, and appears to have **lost the EU region**. The size ceiling rises 4×; the region coverage may fall to the US.

#### 3. lifecycle — **partly** (1.x: partly)

- **Figure:** `No Linux stop; 24/48 h`
- **Scenario:** Stopping the box to save money is not an option on Linux: there is no stop or pause, and at 24 hours (Starter) the sandbox is deleted, memory and all.
- **Note:** Linux only runs or is deleted. Windows keeps its disk across stop and start. A persistent macOS sandbox stops, starts, pauses with memory and forks. Every sandbox is deleted when its wall-clock timeout fires; the organisation maximum is 86,400 s (24 h) on Starter and 48 h on Team, and a timeout once set cannot be cleared. This is the single biggest buyer-facing change from 1.x, where containers stopped and archived and VMs paused.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/sandboxes.md — "| **Stop and start**         | ✗               | ✓ persistent     | ✓ persistent     | ✗            |" — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "Every Linux sandbox supports wait for state, delete, timeouts, and lifecycle policy updates." — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "Once set, the timeout cannot be cleared." — docs-confirmed
  - ↳ https://www.daytona.com/pricing.md — "Sessions up to 24 hours" — pricing-page
  - ↳ https://www.daytona.com/pricing.md — "Sessions up to 48 hours" — pricing-page
- **Differs from 1.x:** 1.x containers stopped (filesystem kept, memory lost) and archived after 7 days; 1.x Linux VMs paused with memory. 2.0 Linux has neither: the only terminal state is deleted. A 24/48 h session cap is new and applies to every class.

#### 4. snapshots-forks — **partly** (1.x: partly)

- **Figure:** `Memory: persistent/warm only`
- **Scenario:** Capturing a running Python server with its memory works on a persistent sandbox or one served from a warm template; from an ordinary ephemeral sandbox you can capture only the filesystem as an image.
- **Note:** A full snapshot saves memory and disk and restores with the processes still running. Only a persistent Linux sandbox or one served from a warm template can be captured; a sandbox created from a filesystem snapshot or with a volume attached is refused with 409, and the docs never define *persistent* or *warm template* for Linux. GPU checkpoints add GPU memory. macOS snapshots are disk-only images of a stopped persistent sandbox, and macOS fork copies the disk, not memory. Windows supports neither. Snapshots are named, kept until deleted, restore any number of times, and outlive the source.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/snapshots.md — "A snapshot is a capture of the memory and disk of a running sandbox, saved under a name." — docs-confirmed
  - ↳ https://www.daytona.com/docs/snapshots.md — "A Linux sandbox produces a full snapshot, and only a persistent sandbox or one served from a warm template can be captured." — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "The source sandbox must be persistent or served from a warm template. A snapshot of any other sandbox, such as one created from a filesystem snapshot or with volumes attached, fails with `409`." — docs-confirmed
  - ↳ https://www.daytona.com/docs/sandboxes.md — "| **Memory snapshot**        | ✓ warm template | ✗                | ✗                | ✓ checkpoint |" — docs-confirmed
  - ↳ https://www.daytona.com/docs/macos-sandboxes.md — "A fork does not copy memory, and a fork that asks for memory fails." — docs-confirmed
  - ↳ https://www.daytona.com/docs/snapshots.md — "Windows sandboxes do not support snapshots." — docs-confirmed
- **Differs from 1.x:** 1.x had cold filesystem snapshots on containers, hot filesystem+memory snapshots on VMs, and fork of a running Linux VM. 2.0 keeps filesystem capture (as an image) but gates memory snapshots behind an undefined *persistent* or *warm template* class, and moves live fork to persistent macOS only (Linux copies are snapshot restores).

#### 5. storage — **partly** (1.x: partly)

- **Figure:** `NVMe free; volume $0.000108`
- **Scenario:** Postgres in `/var/lib` survives only if `/var/lib` is on a volume; the sandbox's own NVMe is free but goes when the sandbox does, and the volume commits in the background.
- **Note:** Ephemeral NVMe is free and dies with the sandbox. A volume is project storage mounted at a path: 1–1000 GiB, up to 8 per sandbox, $0.000108/GiB-hour, attachable to several sandboxes at once. A disk volume is an ext4 private copy committed in the background at most every 5 s and only after ~1 s of no writes, merged per path with the newest modification time winning; a bucket volume is a live S3 bucket, and read-only mounts are bucket-only. Volume traffic bills per uploaded GiB, downloaded GiB and 1,000 requests at unpublished rates. Windows and GPU sandboxes attach no volumes.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/persistence.md — "The writable filesystem of a Daytona sandbox exists only while the sandbox does." — docs-confirmed
  - ↳ https://www.daytona.com/docs/volumes.md — "A volume is persistent, project-scoped storage that a sandbox mounts as a directory." — docs-confirmed
  - ↳ https://www.daytona.com/docs/volumes.md — "A sandbox attaches up to 8 volumes, and several sandboxes can attach the same volume at once." — docs-confirmed
  - ↳ https://www.daytona.com/docs/volumes.md — "A commit runs at most every 5 seconds, and only once the sandbox has stopped writing to the volume for about 1 second." — docs-confirmed
  - ↳ https://www.daytona.com/docs/volumes.md — "The version with the newer modification time is kept." — docs-confirmed
  - ↳ https://www.daytona.com/docs/volumes.md — "Traffic to a bucket volume is billed per uploaded GiB, downloaded GiB, and 1,000 requests" — docs-confirmed
  - ↳ https://www.daytona.com/pricing.md — "| Volumes (Stateful) | — | $0.000108 |" — pricing-page
- **Differs from 1.x:** 1.x persisted the whole disk across stop and billed it while stopped at the same $0.000108, and sold S3-backed FUSE volumes free (100 per organisation, not counted against storage). 2.0 makes the disk ephemeral and free while running, and the volume the paid persistence object. Postgres now needs a volume, not just a stopped sandbox.

#### 6. idle-timers — **partly** (1.x: partly)

- **Figure:** `Idle delete; 24/48 h cap`
- **Scenario:** Set a one-hour idle timeout and the box is deleted, not paused; leave it unset and the wall-clock timeout still deletes it at 24 hours.
- **Note:** The idle timeout is off by default, has a 60 s minimum, and its only Linux action is delete (stop on Windows, stop on persistent macOS); it fires within about 2 minutes of the interval. Activity is any toolbox request, preview request, VNC or SSH traffic, a running toolbox command, create/start, or a manual reset. A wall-clock timeout starts at boot, is not extended by activity, cannot be cleared once set, and is capped by the organisation maximum: 24 h on Starter, 48 h on Team. The docs also mention a platform default of 300 s *if the platform default is enabled*, which no page confirms for a new organisation.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "The idle timeout is off by default unless the project sets one, has a minimum of 60 seconds, and requires an action." — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "The idle timeout fires after the sandbox has had no activity for the interval. Activity is any request through the toolbox API, preview URLs, VNC, and SSH" — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "The timeout is a wall-clock budget. It starts when the sandbox starts running. Activity does not extend it." — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "Without a project default, Daytona applies the platform default timeout of 300 seconds, if the platform default is enabled." — docs-confirmed
  - ↳ https://www.daytona.com/docs/linux-sandboxes.md — "An explicit timeout must not exceed the organization maximum, 86,400 seconds (24 hours) unless the organization sets a different maximum." — docs-confirmed
- **Differs from 1.x:** 1.x defaulted containers to a 15-minute idle stop (which archived after 7 days) and VMs to a 60-minute idle pause, and a sandbox could run indefinitely with the interval set to 0. 2.0 has no default idle timer at all (off unless the project sets one), the timer deletes rather than pauses, and a hard 24/48 h session cap makes "run indefinitely" impossible. The 1.x complaint that the 15-minute stop ignored a running build is gone; the 24-hour deletion is the new version of the same problem.

#### 7. reaching-it — **yes** (1.x: partly)

- **Figure:** `Preview, SSH, terminal`
- **Scenario:** A dev server gets a public or signed preview link, a colleague opens the same box over SSH or the browser terminal, and a local port forward reaches the database.
- **Note:** Preview URLs are per port, private by default and public on request; a signed URL is per port, revocable, 1 s to 7 days (60 s default). The API's standard token is sandbox-wide, never expires and survives restarts; the SDK's port token lasts 1 hour. SSH is a gateway on 2222 with `-L` forwarding (no `-R`, no agent forwarding) and a stable ed25519 host key per region; there is a web terminal and a VNC desktop. A request to a non-running sandbox returns 409, so nothing wakes on a request. The URL is built from the sandbox ID, so a recreated sandbox gets a new URL.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/preview.md — "Daytona provides preview URLs for accessing services running in your sandboxes." — docs-confirmed
  - ↳ https://www.daytona.com/docs/preview.md — "Private endpoints require authentication; public ones do not." — docs-confirmed
  - ↳ https://www.daytona.com/docs/preview.md — "The token returned by the preview URL API is bound to the sandbox and grants access to every private preview endpoint on it. It does not expire and stays the same across sandbox restarts." — docs-confirmed
  - ↳ https://www.daytona.com/docs/preview.md — "Each link is valid for one port, expires at a set time, and can be revoked on its own. The expiry ranges from 1 second to 7 days, with a default of 60 seconds." — docs-confirmed
  - ↳ https://www.daytona.com/docs/preview.md — "Any request to a sandbox that is not running receives 409." — docs-confirmed
  - ↳ https://www.daytona.com/docs/ssh-access.md — "Local forwarding uses the `-L` flag." — docs-confirmed
  - ↳ https://www.daytona.com/docs/web-terminal.md — "Daytona provides a browser-based web terminal for your sandboxes." — docs-confirmed
- **Differs from 1.x:** 1.x was `partly`: the only token was sandbox-wide and unrevokable, and no local forwarding was documented. 2.0 keeps the sandbox-wide non-expiring token as the API default (a real catch) but adds revocable per-port signed URLs, a 1-hour port token for SDK users, `-L` forwarding, and a browser terminal and desktop. The remaining sharp edge is that the standard token is still all-ports and immortal.

#### 8. custom-domains — **partly** (1.x: partly)

- **Figure:** `Beta on Team; own proxy`
- **Scenario:** On Team you attach demo.acme.com as a beta; on Starter you run your own proxy under the domain and forward to the preview URL.
- **Note:** Custom domains (Beta) is listed for Team and Enterprise only. No page documents how to attach one, what certificate is used, whether it survives a recreate, or how it authenticates. The preview page documents the other route: your own proxy, forwarding to the standard preview URL with a credential, which Daytona strips before the request reaches the sandbox. The default host is a Daytona subdomain containing the sandbox ID, so a recreated sandbox changes URL unless the beta or your proxy hides it.
- **Evidence:**
  - ↳ https://www.daytona.com/pricing.md — "Custom domains (Beta)" — pricing-page
  - ↳ https://www.daytona.com/docs/preview.md — "Place your own proxy in front of preview URLs to serve previews on a custom domain" — docs-confirmed
  - ↳ https://www.daytona.com/docs/preview.md — "Daytona strips the credential headers before the request reaches the sandbox." — docs-confirmed
- **Differs from 1.x:** 1.x was `partly` with only the own-proxy route and no automatic HTTPS. 2.0 adds a native Team/Enterprise beta but publishes no page for it, so the documented route is still your proxy; `auto-https` remains unpublished.

#### 9. outbound-network — **partly** (1.x: partly)

- **Figure:** `Open egress; static IP Beta`
- **Scenario:** `pip install` works on any plan because egress is open by default; a vendor that whitelists IPs needs the Team beta, and a secret's host allowlist is a separate control.
- **Note:** Egress is open by default. A per-sandbox policy can block everything or allow up to 128 domains and IPv4 CIDRs combined, with DNS filtered to the allowlist; IPv6, private ranges and nested entries are rejected, and Windows/GPU sandboxes accept no policy. Static egress IPs are a Team/Enterprise beta with no documentation, count or price. No egress price or allowance is published; bucket-volume traffic is metered per uploaded GiB, downloaded GiB and 1,000 requests.
- **Evidence:**
  - ↳ https://www.daytona.com/docs/network-limits.md — "Egress is open by default." — docs-confirmed
  - ↳ https://www.daytona.com/docs/network-limits.md — "Max 128 entries" — docs-confirmed
  - ↳ https://www.daytona.com/docs/network-limits.md — "IPv4 only" — docs-confirmed
  - ↳ https://www.daytona.com/docs/network-limits.md — "Windows and GPU sandboxes do not accept them." — docs-confirmed

#### Isolation (5)

**`own-vm`** — **yes** — `Firecracker microVM` — Δ up from partly.
Every sandbox is a VM with its own kernel. Linux is Firecracker, Windows and GPU are Cloud Hypervisor, macOS is Apple's Virtualization framework; there is no container class left.
↳ https://www.daytona.com/docs/sandboxes.md — "A sandbox is a hardware-isolated virtual machine with its own kernel, filesystem, network stack, and allocated vCPU, RAM, and disk, with isolation enforced by the hypervisor." — docs-confirmed
↳ https://www.daytona.com/docs/linux-sandboxes.md — "Linux sandboxes are **Linux virtual machines (VMs)**." — docs-confirmed

**`root`** — **yes** — `root or image user`.
The default OS user is the image's `USER`, or `root` when the image sets none, sets root, or sets a numeric ID; a command can also name any user that exists in the image. Root is available but not forced.
↳ https://www.daytona.com/docs/linux-sandboxes.md — "The default is the image's `USER`, or `root` if the image sets none, sets root, or sets a numeric user ID." — docs-confirmed

A full Docker Engine, not a shim. Daytona does not install it: the sandbox image must ship it, and the documented `docker-dind` image does. Docker data lives on the sandbox disk and is kept by captured images and snapshots.
↳ https://www.daytona.com/docs/docker.md — "Docker runs inside a sandbox as a full Docker Engine, so workloads can build images and run containers the same way they do on a regular Linux machine." — docs-confirmed
↳ https://www.daytona.com/docs/docker.md — "Daytona does not install Docker. When the sandbox image ships Docker Engine, the sandbox starts it automatically on every boot; when the image does not, nothing starts." — docs-confirmed

**`custom-image`** — **yes** — `OCI, Dockerfile, capture`.

#### Snapshots and forks (6)

**`snapshot-files`** — **yes** — `image capture`.
Capture the filesystem of a running Linux or Windows sandbox as a named image; new sandboxes boot from it. The source keeps running during the capture. A macOS filesystem snapshot is the disk of a stopped persistent sandbox.
↳ https://www.daytona.com/docs/images.md — "Capture the filesystem of a sandbox as an image, and boot new sandboxes from the image." — docs-confirmed

**`snapshot-memory`** — **partly** — `persistent/warm only`.
Shortfall: A full snapshot keeps memory and disk, but only a persistent Linux sandbox or one served from a warm template can be captured; a sandbox created from a filesystem snapshot or with a volume attached is refused with 409, and the docs never define persistent or warm template for Linux.
↳ https://www.daytona.com/docs/snapshots.md — "A snapshot is a capture of the memory and disk of a running sandbox, saved under a name." — docs-confirmed
↳ https://www.daytona.com/docs/linux-sandboxes.md — "The source sandbox must be persistent or served from a warm template. A snapshot of any other sandbox, such as one created from a filesystem snapshot or with volumes attached, fails with `409`." — docs-confirmed

**`fork-running`** — **partly** — `macOS fork; Linux restore` — Δ down from yes.
Shortfall: A persistent macOS sandbox forks in place but copies only its disk, not memory; on Linux a copy is a full-snapshot restore into a new sandbox, which needs a persistent or warm-template source and gives the copy a new IP.
↳ https://www.daytona.com/docs/macos-sandboxes.md — "Fork a persistent macOS sandbox to copy its disk into a new sandbox. A fork does not copy memory, and a fork that asks for memory fails." — docs-confirmed
↳ https://www.daytona.com/docs/snapshots.md — "Several sandboxes restore from the same snapshot, and each continues on its own." — docs-confirmed

**`older-snapshot`** — **yes** — `named, any number`.
Snapshots are named objects kept until deleted, not a rolling latest-only slot. Deleting the source sandbox does not delete its snapshots, and any number of sandboxes can restore from the same one.
↳ https://www.daytona.com/docs/snapshots.md — "Deleting the source sandbox does not affect its snapshots." — docs-confirmed

**`templates`** — **yes** — `images + snapshots`.
Two template objects: an image is the filesystem a sandbox boots from (OCI, Dockerfile build, or capture); a snapshot is memory plus disk of a running sandbox that new sandboxes resume from.
↳ https://www.daytona.com/docs/images.md — "A sandbox set up by hand or by an agent is captured, and new sandboxes start from its filesystem." — docs-confirmed
↳ https://www.daytona.com/docs/persistence.md — "A restored sandbox continues with its processes still running." — docs-confirmed

**`backups`** — **not-published** — `v0 only` — Δ sideways from no.
The only "backup" in the 2.0 docs is the Daytona v0 backup used when importing an archived sandbox: the migration page reports `last_backup_at` and refuses an import whose backup is incomplete. No v2 schedule, retention window, export path or restore-to-new-machine flow is documented. Silence, so `not-published` rather than `no`.
↳ https://www.daytona.com/docs/migrate-from-v0.md — "When Daytona v0 last completed a backup of the sandbox, or `null`." — docs-confirmed
↳ https://www.daytona.com/docs/migrate-from-v0.md — "Daytona v0 has not completed a backup of the sandbox." — docs-confirmed

#### Storage (5)

**`files-survive-stop`** — **partly** — `Windows/macOS only` — Δ down from yes.
Shortfall: A Linux sandbox has no stop at all — it runs until it is deleted and then loses its disk — so files survive a stop only on Windows or a persistent macOS sandbox, and survive a Linux delete only on a volume or a captured image.
↳ https://www.daytona.com/docs/windows-sandboxes.md — "A persistent Windows sandbox keeps its disk across stop and start." — docs-confirmed
↳ https://www.daytona.com/docs/sandboxes.md — "| **Filesystem persistence** | ✗               | ✓                | ✓                | ✗            |" — docs-confirmed
↳ https://www.daytona.com/docs/persistence.md — "The writable filesystem of a Daytona sandbox exists only while the sandbox does." — docs-confirmed

**`volumes`** — **yes** — `$0.000108/GiB-h`.
Project-scoped storage mounted at a path, 1–1000 GiB, surviving the sandbox and reattachable to a later one. Disk volumes are ext4 with background commits; bucket volumes are S3. Billed per GiB-hour, not free (a change from 1.x).
↳ https://www.daytona.com/docs/volumes.md — "A volume is persistent, project-scoped storage that a sandbox mounts as a directory." — docs-confirmed
↳ https://www.daytona.com/pricing.md — "| Volumes (Stateful) | — | $0.000108 |" — pricing-page

**`shared-volume`** — **yes** — `8 per sandbox`.
Up to 8 volumes per sandbox, and several sandboxes can attach the same volume at once. Writes are merged per path with the newest modification time winning, so a shared volume is last-writer-wins per file, not transactional; a bucket volume is live and supports read-only mounts.
↳ https://www.daytona.com/docs/volumes.md — "A sandbox attaches up to 8 volumes, and several sandboxes can attach the same volume at once." — docs-confirmed
↳ https://www.daytona.com/docs/volumes.md — "The version with the newer modification time is kept." — docs-confirmed

**`mount-buckets`** — **yes** — `S3 and S3-compatible`.
A bucket volume mounts an S3 bucket live inside the sandbox; Daytona can own a managed bucket, or you bring an external one on AWS S3 or an S3-compatible service with credentials stored as project secrets. Read-only mounts are supported for bucket volumes only.
↳ https://www.daytona.com/docs/volumes.md — "an external bucket volume mounts a bucket you own" — docs-confirmed
↳ https://www.daytona.com/docs/volumes.md — "Only bucket volumes support read-only mounts." — docs-confirmed

**`big-disk`** — **yes** — `256 GiB; 1 TiB volume` — Δ up from no.
A Linux sandbox's writable disk goes to 256 GiB (the 1.x cap was 10 GiB), and a single volume to 1000 GiB. The pricing page claims 512 GiB–3 TiB per plan, which the limits page does not support.
↳ https://www.daytona.com/docs/sandboxes.md — "A Linux sandbox may guarantee at most 16 cores, 32GiB memory, and 256GiB disk." — docs-confirmed
↳ https://www.daytona.com/docs/volumes.md — "from `1` to `1000` GiB" — docs-confirmed
↳ https://www.daytona.com/pricing.md — "| Ephemeral disk | 512 GiB | 1 TiB | 3 TiB |" — pricing-page

#### Idle timers (4)

**`stay-on`** — **partly** — `24 h Starter / 48 h Team` — Δ down from yes.
Shortfall: Nothing stays up for a week: every sandbox is deleted when its wall-clock timeout fires, and the organisation maximum is 24 hours on Starter and 48 on Team (Enterprise custom), so a long-lived agent must recreate itself and its disk from a volume or image.
↳ https://www.daytona.com/docs/linux-sandboxes.md — "An explicit timeout must not exceed the organization maximum, 86,400 seconds (24 hours) unless the organization sets a different maximum." — docs-confirmed

**`choose-idle`** — **yes** — `60 s+, off by default`.
You set the idle interval per sandbox or as a project default; it is off unless set, has a 60-second minimum, accepts any larger value, and fires within about two minutes. The action on Linux is delete. The wall-clock timeout is a separate setting and cannot be cleared once set.
↳ https://www.daytona.com/docs/linux-sandboxes.md — "The idle timeout is off by default unless the project sets one, has a minimum of 60 seconds, and requires an action." — docs-confirmed

**`wake-on-request`** — **no** — `409, no wake`.
A request to a sandbox that is not running returns 409; nothing starts it. A stopped Windows or persistent macOS sandbox must be started by an API call, and a deleted Linux sandbox cannot be reached at all.
↳ https://www.daytona.com/docs/preview.md — "Any request to a sandbox that is not running receives 409." — docs-confirmed

**`schedules`** — **not-published** — `no scheduler` — Δ sideways from no.
The docs describe two timers, both of which delete or stop the sandbox, and a reset call; no cron, job or scheduled-create object appears in the API reference, CLI reference or docs index. A schedule has to live in your own code calling the API. Silence, so `not-published`.

#### Reaching it (8)

**`public-url`** — **yes** — `per-port public`.
Any HTTP listener on ports 1–65535 gets a preview URL; visibility is per port, and a port can be made public so no credential is needed.
↳ https://www.daytona.com/docs/preview.md — "Private endpoints require authentication; public ones do not." — docs-confirmed

**`private-url`** — **yes** — `token or signed link`.
Private is the default. Two credentials: a standard preview token in `x-daytona-preview-token`, or a signed URL with the token in the hostname. Signed links are per port, revocable individually, and expire from 1 second to 7 days.
↳ https://www.daytona.com/docs/preview.md — "Each call mints a new token that is valid for a single port and can be revoked individually before it expires." — docs-confirmed

**`ssh`** — **yes** — `gateway on 2222`.
A real SSH client against a per-region gateway on port 2222; the credential travels in the username as `sandboxId#token` and can be a sandbox access token or a project API key. `scp`/`sftp` work; the gateway presents one stable ed25519 host key per region.
↳ https://www.daytona.com/docs/ssh-access.md — "Daytona provides SSH access to sandboxes through an SSH gateway" — docs-confirmed

**`web-terminal`** — **yes** — `dashboard PTY`.
A full terminal in the dashboard, backed by a PTY, with multiple sessions, scrollback, and `Open terminal here` from the file browser. Gated by the project key's sandbox-write permission; it is not exposed by making a preview public.
↳ https://www.daytona.com/docs/web-terminal.md — "Daytona provides a browser-based web terminal for your sandboxes." — docs-confirmed

**`tunnel`** — **yes** — `ssh -L` — Δ up from not-published.
Local port forwarding works through the SSH gateway (`-L 8080:localhost:8080`), including from the CLI's SSH command. Remote forwarding (`-R`), Unix-socket forwarding and agent forwarding are refused.
↳ https://www.daytona.com/docs/ssh-access.md — "Local forwarding uses the `-L` flag." — docs-confirmed
↳ https://www.daytona.com/docs/ssh-access.md — "Remote forwarding (`-R`): rejected" — docs-confirmed

**`raw-tcp`** — **partly** — `SSH -L only` — Δ up from not-published.
Shortfall: A non-HTTP service is reachable only through an SSH local forward; the public preview URLs carry HTTP and WebSocket, and although a port mapping can declare UDP there is no documented public address or protocol for a raw TCP or UDP service.
↳ https://www.daytona.com/docs/preview.md — "Any process listening for HTTP traffic on ports 1 to 65535 can be previewed through a generated URL." — docs-confirmed
↳ https://www.daytona.com/docs/linux-sandboxes.md — "Each mapping has a `port` and a `proto`, which defaults to `tcp`." — docs-confirmed

**`custom-domain`** — **partly** — `Team beta / own proxy`.
Shortfall: Custom domains are a Team and Enterprise beta with no documentation of how to attach one or what certificate is used, so on Starter the only route is your own proxy under your domain forwarding to a Daytona preview URL.

#### Keys and secrets (3)

**`secrets-store`** — **yes** — `project secrets`.
Secrets are project-scoped, encrypted at rest, never returned by the API after creation, attached to a sandbox by name, and injected into outbound HTTPS by a proxy. The sandbox sees an opaque placeholder, not the value.
↳ https://www.daytona.com/docs/secrets.md — "Secrets store sensitive values such as API keys, tokens, and passwords for use across your Daytona sandboxes." — docs-confirmed
↳ https://www.daytona.com/docs/secrets.md — "encrypted at rest and never returned by the API after creation" — docs-confirmed

**`hidden-secrets`** — **yes** — `TLS proxy`.
The proxy replaces the placeholder in the request line, query string, every header and the body, only for hosts on the secret's allowlist, and dials the destination itself. Catches: HTTPS only, 1 MiB body limit, HTTP/1.1 only, certificate-pinned clients fail, and an echoing host returns the value.
↳ https://www.daytona.com/docs/secrets.md — "without ever placing the plaintext inside the sandbox" — docs-confirmed
↳ https://www.daytona.com/docs/secrets.md — "The proxy substitutes placeholders in the request line and query string, in every request header, and in the request body." — docs-confirmed

**`scoped-keys`** — **yes** — `project + scopes`.
Every project API key belongs to exactly one project, carries an explicit permission list and an optional expiry; requests are confined to both. Revocation applies to new requests, with up to 30 s of grace at a regional proxy. Organization keys are a separate, narrower type.
↳ https://www.daytona.com/docs/api-keys.md — "Every project API key belongs to exactly one project and carries an explicit list of [permissions](#scopes); its requests are confined to both." — docs-confirmed
↳ https://www.daytona.com/docs/api-keys.md — "Keys can carry an expiry. Revocation applies to new requests; a regional proxy can accept a revoked key for up to 30 seconds." — docs-confirmed

### 3.2 Conversions used below

- **core → vCPU:** 1 core = 2 vCPU (SMT on). `$0.101/core-hour ÷ 2 = $0.0505/vCPU-hour`. Mid `$0.168 ÷ 2 = $0.084`; top `$0.235 ÷ 2 = $0.1175`. On non-SMT hardware (Graviton, Apple) the same 2-vCPU shape is 2 cores and costs `$0.202/h`.
- **GiB-hour → GiB-month:** `× 730`. Volume `$0.000108 × 730 = $0.07884/GiB-month`. A 20 GiB volume is `$1.5768/month`; a 50 GiB volume is `$3.942/month`.
- **core-hour → vCPU-hour:** `÷ 2` for CPU, Windows and macOS OS rates.
- **preemptible → on-demand:** `÷ 0.7` (or `× 1.4286`). The published preemptible numbers are rounded to 4 significant figures, so use the on-demand column as the source and `× 0.7` for spot.
- **No currency conversion:** everything is USD, the provider's own list currency. No VAT or tax is added (the pages do not state a treatment; the site's convention is list price).

**What the card cannot express, and the modelling choice for each**

1. **Cores vs vCPUs.** No conversion factor. Model the *vCPU* rate ($0.0505) so A/B/C keep their 2/4/2-vCPU shapes; record that a core is 2 vCPUs, that Graviton/Apple shapes cost 2× per vCPU, and that turning SMT off doubles $/vCPU at the same core price.
2. **Guarantee + limit (two-dimensional meter).** One CPU meter, `allocated` or `active`. Model the guarantee (`allocated`) because it is the billed minimum and the common case; record that a burst above the guarantee is billed measured and is *not* in the total. A "fixed shape" (limit = guarantee) is exact under this model.
3. **CPU-type multiplier.** One `cpu.rate`. Model baseline ($0.101/core); record mid ×1.6667 ($0.168) and top ×2.3313 ($0.235). A reader on Zen 5 pays 2.33× the card.
4. **Region multiplier.** One flat rate. Model `earth` (1.0×); record 1.15–2.0× for named regions. Every real US region costs more than the card.
5. **Spot / preemptible.** No field. Model on-demand (the default); record 0.7× and give the spot A/B/C in §3.6. Do not model spot as the card — a default sandbox is on-demand.
6. **Bucket-volume traffic.** Three tariffs (upload GiB, download GiB, 1k requests) with unpublished rates. `egress.perGiB: null` plus a note; do not invent a number, do not use 0.
7. **macOS Mac reservation.** A 24-hour block at $60.08 per Mac, not a per-resource meter; "macOS sandboxes are not metered". No `Shape` field for a class or a 24-hour minimum. Leave macOS out of the card and price it in prose; adding a 12-core/24-GiB/220-GiB shape would silently price Linux workloads of that size as Macs.
8. **One-time credit vs monthly credit.** `Plan.credit` is monthly. Starter's $200 goes in `note`, `credit: 0`; Team's $100 is `credit: 100` and also expires monthly.
9. **Expiring credits.** `credit` is silent on expiry. Note it on Team; the effect is that unused credit is lost, so Team's effective price is $250 + usage − min(100, usage) and never less than $250.
10. **Plan entitlements (members, sandboxes, GPUs, Windows cores, Mac reservations, OTel retention, SSO, audit, custom domains, static IPs).** No fields. Notes and the profile's `billing.planFee` / `teams-accounts` row.
11. **Project budgets as a hard cap.** `Plan.capped` means a free allowance that refuses work, not a dollar budget. No field. Note it; the `spend-cap` capability row carries the detail.
12. **CPU-type/region/spot multipliers compound.** The engine multiplies nothing; the card's flat rate is the 1.0× baseline. Note the compounding; do not pre-multiply the card, or every reader outside the US pays a rate they were never quoted.
13. **1-core-per-8-GiB floor.** No field. A/B/C satisfy it; a 0.125-core/8-GiB request would be raised. Note it.
14. **Minimum 10 GiB disk when any resource is set.** No field. A/B/C satisfy it (10, 50, 20). Note it.
15. **Disk "billed as measured", not provisioned.** `disk.running: 0` hides it for ephemeral; for a volume the model bills `size_gib`, while the docs define `size_gib` as the capacity of each sandbox's private copy and expose `used_bytes` separately. Which one is billed is not published — model provisioned size, flag it.
16. **Unpublished snapshot/image storage.** "Unlimited snapshots" by plan with no storage price. A note; not a zero.

### 3.5 A, B and C by hand

Inputs, from `presets.a/b/c`:

| Case | Shape | Time | Busy | Disk |
|---|---|---|---|---|
| A | 2 vCPU / 4 GiB / 10 GiB, tasks | 1,000 × 10 min = **166.6667 h** | 50% | deleted each run |
| B | 4 vCPU / 8 GiB / 50 GiB, one machine | 24 × 30 = **730 h** | 10% | kept |
| C | 2 vCPU / 4 GiB / 20 GiB, one machine | 3 × 30 = **90 h** running, **640 h** stopped | 10% | kept |

On SMT hardware, 2 vCPU = 1 core and 4 vCPU = 2 cores. `$0.101` per core-hour becomes `$0.0505` per vCPU-hour; `$0.0162` per GiB-hour is unchanged. Busy fraction does not enter the bill: the guarantee is billed whether the CPU works or waits, and a fixed shape's limit equals its guarantee.

**A — 1,000 ten-minute tasks, 2 vCPU / 4 GiB / 10 GiB**

```
CPU     166.6667 h × 1 core  × $0.101  = $16.8333
Memory  166.6667 h × 4 GiB   × $0.0162 = $10.8000
Disk    166.6667 h × 10 GiB  × $0.000  = $0.0000   (ephemeral NVMe is free)
                                        ---------
                                          $27.6333  →  $27.63
```

The $200 Starter credit covers **7.24 months** of A. Spot: `166.6667 × (0.0707 + 4 × 0.01134) = $19.34`.

**B — one always-on box, 4 vCPU / 8 GiB / 50 GiB, 730 h**

```
CPU     730 h × 2 cores × $0.101  = $147.460
Memory  730 h × 8 GiB   × $0.0162 = $ 94.608
Disk    730 h × 50 GiB  × $0.000  = $  0.000   (ephemeral NVMe is free)
Volume  730 h × 50 GiB  × $0.000108 = $3.942   (the files, across the session cap)
                                     ---------
                                       $246.010  →  $246.01
```

Without the volume, **$242.07** — but the files go when the 24-hour session ends. A 730-hour single session exceeds both plans, so B is priced as one machine-month that is recreated about 30 times (Starter) or 15 times (Team) from an image or the volume. Spot: `730 × (2 × 0.0707 + 8 × 0.01134) = $169.45` plus `$2.76` of spot-priced volume = **$172.21**.

**C — 2 vCPU / 4 GiB / 20 GiB, 90 h running, 640 h "stopped"**

```
CPU     90 h × 1 core × $0.101   = $ 9.090
Memory  90 h × 4 GiB  × $0.0162  = $ 5.832
Volume  730 h × 20 GiB × $0.000108 = $ 1.5768   (the volume bills while the sandbox is gone)
                                   ---------
                                     $16.4988  →  $16.50
```

A Linux sandbox cannot be stopped, so the 640 idle hours are a **deleted** sandbox with its 20 GiB on a volume, not a paused one. If you leave it running instead, C costs `730 × (0.101 + 4 × 0.0162) = $121.03`. Spot: `90 × 0.11606 = $10.45` plus `$1.10` of spot-priced volume = **$11.55**.

**Which plan wins**

| Workload | Starter (fee $0) | Team (fee $250, $100 credit) | Cheaper |
|---|---:|---:|---|
| A | **$27.63** | $250.00 (credit covers all $27.63) | Starter by $222.37 |
| B | **$246.01** | $396.01 ($250 + $246.01 − $100) | Starter by $150.00 |
| C | **$16.50** | $250.00 (credit covers all $16.50) | Starter by $233.50 |

Starter wins every case. Team is **never** cheaper on the same usage, because its $100 credit is $150 less than its $250 fee: `Team − Starter = 250 − min(100, usage) ≥ 150`. Team is a features purchase — unlimited members, 5,000 vs 100 sandboxes, 48 vs 24-hour sessions, custom domains, static egress IPs, RBAC and project budgets — not a discount. The only case where Team is the *right* answer on price is one the calculator cannot express: a team of more than three people, or more than 100 concurrent sandboxes, where Starter's limit, not its bill, is the constraint. Enterprise is custom and not modelled; its 64-core/256-GiB caps, BYOC, SSO, audit logs, HIPAA and KVM access are the reasons to talk to sales.

Credit arithmetic: `$200 / $27.63 = 7.24` months of A, `$200 / $246.01 = 0.81` months of B, `$200 / $16.50 = 12.1` months of C.

## 4. Profile, routes, docs and contradictions

### 4.1 First-party contradictions (both sides, and the interpretation used)

These are the ones a buyer will hit. The profile's `caveats` should carry the first six; the rest belong in the research notes or in `billing`/`sizes` prose.

**C1. Three different size ceilings.** Docs platform maximum 16 cores / 32 GiB / 256 GiB; docs plan caps Starter 4 cores / 16 GiB and Team 8 / 32; pricing plan table 64 cores / 128 GiB for both, with 512 GiB / 1 TiB / 3 TiB disk; pricing FAQ repeats "Sandboxes up to 64 cores, 128 GiB of memory".

`↳ https://www.daytona.com/docs/sandboxes.md — "A Linux sandbox may guarantee at most 16 cores, 32GiB memory, and 256GiB disk." — docs-confirmed`

`↳ https://www.daytona.com/docs/limits.md — "Starter | 4 | 16384" — docs-confirmed`

`↳ https://www.daytona.com/pricing.md — "| Cores | 64 | 64 | Custom |" — pricing-page`

`↳ https://www.daytona.com/pricing.md — "Sandboxes up to 64 cores, 128 GiB of memory, and 1 GPU." — pricing-page`

*Interpretation used:* the limits page is the enforced one (it describes a 400 that names the plan limit, and the plan API reports the caps); the pricing table looks like the Enterprise row copied across. Consequence: **a 64-core sandbox cannot be bought on Starter or Team**, and a 16-core sandbox needs Enterprise. The pricing page's 512 GiB–3 TiB disk is likewise not reachable while the platform disk cap is 256 GiB.

**C2. Linux has no stop, but a "persistent Linux sandbox" is required for snapshots.** Lifecycle matrix: stop/start ✗, pause/resume ✗, fork ✗, filesystem persistence ✗ for Linux. Snapshots: a full snapshot needs "a persistent sandbox or one served from a warm template"; the 409 text says a sandbox created from a filesystem snapshot or with volumes attached cannot be captured. Migration: an imported v0 sandbox becomes "a new persistent sandbox". Process execution: "A session survives pause and resume, but not stop and start."

`↳ https://www.daytona.com/docs/sandboxes.md — "| **Stop and start**         | ✗               | ✓ persistent     | ✓ persistent     | ✗            |" — docs-confirmed`

`↳ https://www.daytona.com/docs/snapshots.md — "only a persistent sandbox or one served from a warm template can be captured" — docs-confirmed`

`↳ https://www.daytona.com/docs/migrate-from-v0.md — "Import an archived Daytona v0 sandbox as a new persistent sandbox in the default project." — docs-confirmed`

`↳ https://www.daytona.com/docs/process-execution.md — "A session survives pause and resume, but not stop and start." — docs-confirmed`

*Interpretation used:* *persistent* is a class, not the default: imported v0 sandboxes are persistent, and the lifecycle matrix describes the default ephemeral class. *Warm template* is an image pre-booted on a runner. Neither is defined, so the snapshot row is `partly` and the caveat says so. A buyer should assume the ordinary `create()` sandbox is ephemeral and cannot be memory-snapshotted until Daytona publishes the rule.

**C3. The pricing FAQ says stopped and paused sandboxes keep their state and cost nothing; Linux cannot stop or pause, and macOS keeps paying.**
`↳ https://www.daytona.com/pricing.md — "No. CPU and memory are billed only while a sandbox is running, and ephemeral NVMe disk is free. A stopped or paused sandbox keeps its state and is not metered. Volumes are billed separately." — pricing-page`
`↳ https://www.daytona.com/docs/billing.md — "macOS sandboxes are not metered; their Mac reservation is charged instead." — docs-confirmed`
`↳ https://www.daytona.com/docs/macos-sandboxes.md — "You pay for each period when it starts." — docs-confirmed`
*Interpretation used:* the FAQ is a generic 1.x-era statement. It is true for Windows (stop keeps the disk, nothing bills) and false for Linux (no stop exists) and for macOS (the reservation runs to the end of its paid period). The `cheap-pause` row is `partly`.

**C4. Windows and GPU are "coming soon" on their own pages while the price list, plan limits and other docs sell them.**
`↳ https://www.daytona.com/docs/windows-sandboxes.md — "Windows sandboxes for Daytona v2 are coming soon." — docs-confirmed`
`↳ https://www.daytona.com/docs/gpu-sandboxes.md — "GPU sandboxes for Daytona v2 are coming soon." — docs-confirmed`
`↳ https://www.daytona.com/pricing.md — "| Windows core licenses | 10 | 50 | Custom |" — pricing-page`
`↳ https://www.daytona.com/pricing.md — "| Nvidia B300 | $5.17 | $8.99 |" — pricing-page`
`↳ https://www.daytona.com/docs/preemption.md — "A reclaimed [Windows](/docs/windows-sandboxes) spot sandbox is stopped, with the disk kept, and a start boots Windows from the preserved disk." — docs-confirmed`
*Interpretation used:* both classes are sold and described elsewhere (Windows base images, RDP, Windows core licences, GPU checkpoints, GPU plan limits), so the "coming soon" callouts are stale pre-launch text. The verdicts are `partly` for GPU (because its dedicated page is a stub) and `yes` for Windows where the class is only a capability row; the caveat records the stub pages. If Daytona meant "not available", the price list is selling something it cannot deliver.

**C5. GPU sandboxes cannot be spot, but the price list has a Preemptible GPU column.**
`↳ https://www.daytona.com/docs/preemption.md — "GPU sandboxes cannot be spot, so GPU experiments run at full price." — docs-confirmed`
`↳ https://www.daytona.com/pricing.md — "| Nvidia B300 | $5.17 | $8.99 |" — pricing-page`
*Interpretation used:* the preemptible GPU price is a 1.x legacy column (1.x did sell preemptible GPU sandboxes) and is unreachable in 2.0. Do not use it to discount a GPU workload; the on-demand column is the 2.0 price.

**C6. macOS is "not metered", but the price list has a macOS core-hour rate, and a stopped macOS sandbox keeps billing its reservation.**
`↳ https://www.daytona.com/docs/billing.md — "macOS sandboxes are not metered; their Mac reservation is charged instead." — docs-confirmed`
`↳ https://www.daytona.com/pricing.md — "| macOS | $0.00574 | $0.0082 |" — pricing-page`
`↳ https://www.daytona.com/docs/macos-sandboxes.md — "The price of one reservation of this model is **$2.5032 per Mac-hour, $60.08 per 24-hour period**." — docs-confirmed`
*Interpretation used:* the reservation is the price; the OS rate is unreachable or a component already inside it. Model macOS at $2.5032/Mac-hour (24-hour minimum, no early end), not at $0.0082/core-hour. The consequence is large: a Mac-day is $60.08 whether the sandbox works or waits, and a stopped sandbox does not stop the reservation.

**C7. The SLA's "Tier 4" has no counterpart in the 2.0 plan names.**
`↳ https://www.daytona.com/sla — "Tier 4 and above customers may request a Service Credit." — docs-confirmed`
`↳ https://www.daytona.com/pricing.md — "### Starter" — pricing-page`
*Interpretation used:* the SLA was written for the 1.x top-up tiers (Tier 1–4) and was not re-issued for Starter/Team/Enterprise. A Team customer cannot tell from the documents whether they are "Tier 4". Treat the SLA as a 99.95% promise with an unclear credit gate; the `sla` row is `partly`.

**C8. 2.0 is launched as v2.0.0 but labelled Alpha.**
`↳ https://www.daytona.com/changelog/daytona-2-0.md — "Published: 2026-11-01 · Version: v2.0.0" — docs-confirmed`
`↳ https://www.daytona.io/docs — "v0.231 Latest v2.0 Alpha" — docs-confirmed`
`↳ https://www.daytona.com/docs/cli.md — "The v2 CLI is released as `2.0.0-alpha.N` versions." — docs-confirmed`
*Interpretation used:* the platform is launched and sold; the clients and the 1.x docs' label are alpha. The profile's status should say "researched" (the site's status is about this guide, not the vendor's maturity) and the `whatItIs`/caveats should say "public alpha clients". A buyer who needs a stable SDK should know the Python and TypeScript packages are pre-releases and the 1.x clients are the stable ones.

**C9. The legal and status pages still describe 1.x.**
`↳ https://www.daytona.com/terms-of-service — "Current fees are listed on our Site (at https://www.daytona.io/pricing) or in a mutually agreed written order form." — docs-confirmed`
`↳ https://www.daytona.com/terms-of-service — "Runtime – the secure, scalable, container or microVM environment" — docs-confirmed`
`↳ https://status.app.daytona.io/ — "sandbox create, start, stop and archive" — docs-confirmed`
*Interpretation used:* the terms were last updated 22 Aug 2025, before 2.0, and were not re-issued; the status page still reports 1.x operations. Neither is evidence that 2.0 has archive or containers; they are stale text. The status case is weaker than it looks: 2.0's API reference says "Served at https://app.daytona.io/api", so `app.daytona.io` is the API host for both platforms, and the shared status page is expected. What is still stale is the component list — 2.0 has no archive and no `exec` sandbox creation, and the page does not separate v0 from v2, so a 2.0 buyer cannot read 2.0 uptime from it.

`↳ https://www.daytona.com/docs/api — "Served at https://app.daytona.io/api." — docs-confirmed`

**C10. No EU region is documented, while the DPA offers EU SCCs and the trust centre claims data residency controls.**
`↳ https://www.daytona.com/docs/regions — "United States us · 1.15× US East (Ashburn) us-east · 1.75× Ashburn us-east-ash-1 · 2.0× Boston us-east-bos-1 · 2.0×" — not-published`
`↳ https://www.daytona.com/dpa — "the EU SCCs will be governed by the laws of Ireland" — docs-confirmed`
*Interpretation used:* a legal transfer mechanism is not a European region. The `eu-region` row is `not-published`; the `eu-residency` situation should drop Daytona until the region list is confirmed from an account.

**C11. The 300-second platform timeout vs the 24-hour plan cap.**
`↳ https://www.daytona.com/docs/linux-sandboxes.md — "Daytona applies the platform default timeout of 300 seconds, if the platform default is enabled." — docs-confirmed`
`↳ https://www.daytona.com/docs/linux-sandboxes.md — "An explicit timeout must not exceed the organization maximum, 86,400 seconds (24 hours)" — docs-confirmed`
`↳ https://www.daytona.com/docs/projects.md — "ephemeral": { "timeout_seconds": 1800, "idle_timeout_seconds": 600 }` — docs-confirmed`
*Interpretation used:* the 300 s figure is a default that may or may not be enabled, and the projects example uses 1,800 s. A create that omits a lifecycle policy therefore has an unknown lifetime: somewhere between 5 minutes (if the platform default is on) and 24 hours (the org maximum). The profile should tell a reader to set an explicit timeout. This is an open question, not a settled 300 s default.

**Answer: no dated retirement exists. 1.x is live, sold, documented as "Latest", and still shipping releases after 2.0 launched. ### 5.3 The signals that point the other way

- **Naming.** The 2.0 docs call the old platform "Daytona v0", not "1.x", and its migration path is `migrate-from-v0`. A vendor that intends two products to coexist usually names them as peers ("Daytona 1" and "Daytona 2"); "v0" reads as "the version before the product".
- **Sales surface.** daytona.com's nav and pricing page carry no link to daytona.io and no "still on 1.x?" path; daytona.io's product pages carry no 2.0 banner. The only cross-links are the 1.x docs switcher (which links to 2.0) and the stale daytona.io URLs inside some 2.0 guides (the Claude guide links daytona.io/docs/cli and daytona.io/docs/snapshots). A 1.x customer arriving at the new site sees no route back except the URL they already know; a 2.0 reader following a guide is sent to 1.x docs.
- **Positioning.** The CEO post says the company handed its old customers to competitors and rebuilt. That is a statement about strategy, not about hosting: the old platform is kept for the customers who did not leave, not promoted.
- **Release character.** v0.230.0 is a branch sync and dependency update; v0.231.0 adds one GPU type. That is maintenance cadence, not roadmap cadence. The 2.0 changelog has the roadmap.
- **No deprecation language anywhere.** Searched the 1.x changelog (back to September 2025), the 1.x docs, both pricing pages, the Terms, the SLA, the DPA, the trust centre and all 78 cached 2.0 doc pages for "sunset", "deprecat", "retire", "end of life", "EOL", "legacy", "migration deadline", "1.x" and "v0". The only hits are unrelated: "sunset" is a drawing prompt in the Claude guide; "deprecated" marks the 1.x `target` field and a platform-image flag; "legacy" is a secret-capture status (`unresolved_legacy`); "deprecated workspace routes" is a 1.x API cleanup. No product-end language, no date.

### 5.4 Verdict and how to phrase it

- **Retired?** No.
- **Dated statement?** None found. Not in the changelog, the docs, the pricing pages, the blog, the Terms, the SLA or the trust centre.
- **Best-supported reading:** 1.x is in **maintenance with a live sales page**, 2.0 is the **strategic replacement**, and the vendor has left itself the option to run both indefinitely. The migration tooling is one-way and copy-based, which is what a company builds when it wants customers to move without forcing a date.
- **Do not write** "Daytona 1.x is being retired", "1.x is deprecated", "1.x shuts down in 2027" or "2.0 replaces 1.x on 1 November". None is supported.
- **Safe to write** "Daytona 1.x at daytona.io is still live and still sold; the guide now describes 2.0 at daytona.com. No retirement date is published." That is exactly what the evidence says, and it is useful to a reader who finds a 1.x tutorial.
- **What would change the answer:** a 1.x docs banner, a changelog entry naming a shutdown, a pricing-page notice, or 1.x releases stopping for a quarter. Re-check the 1.x changelog date at the next provider audit; if it has not moved, the maintenance reading strengthens.

### 5.5 One naming trap for the parent

The owner's brief says "Daytona 1.x (daytona.io)" and "Daytona 2.0 (daytona.com)". The vendor says **"Daytona v0"** for the old platform in the 2.0 docs and **"v0.231"** for its docs version, and **"v2.0"** for the new one. The guide's own `changes.json` and profile should use the owner's "1.x" and "2.0" for readers, with one parenthetical "the 2.0 docs call it v0" the first time the old platform is mentioned, so a reader who follows a 2.0 link is not confused. Do not rename the provider ID.
