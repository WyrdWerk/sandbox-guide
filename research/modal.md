> **The one number that changes every cost estimate.** Modal prices CPU per **physical core**, and says "The cpu parameter specifies physical CPU cores (1 core = 2 vCPUs)" — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`. The `cpu=` argument is measured in those same cores. A third-party benchmark reports that `cpu=N` gives a guest that sees **N** CPUs, not 2N. Both readings are presented in §11: the documented one first, the measured one as a sensitivity. They differ by 1.6× on the shared workloads. Do not quote a Modal price without saying which reading it uses.

## 1. What it is, who it is for, product lines

**One paragraph.** Modal Sandboxes are short-lived, isolated Linux containers for running untrusted code — typically code an LLM or an end user produced — inside Modal's serverless compute platform. You create one from Python, JavaScript or Go, run commands in it over an API, stream files in and out, and either let it expire or terminate it. There is no pause: a sandbox runs, then it is finished. Local state outlives it only if you take a snapshot or wrote it to a Volume, and a snapshot always produces a new sandbox rather than reviving the old one. *(Synthesis of the sourced claims below; each element is tagged where it appears.)*

- "This page is a high-level guide to Sandboxes, secure containers for executing untrusted code on Modal." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Sandboxes are useful for tasks like executing code generated by an LLM or isolating user-generated code." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Designed to give agents the computers they need at the scale, speed, and reliability they demand." — [Sandboxes product page](https://modal.com/products/sandboxes) · `docs-confirmed`
- "Isolated environments for coding agents, RL rollouts, and untrusted code" — [pricing page navigation](https://modal.com/pricing) · `pricing-page`

**Who it is for.** Two audiences are named explicitly as headings: "Reinforcement learning rollouts" and "Coding Agents". — [Sandboxes product page](https://modal.com/products/sandboxes) · `docs-confirmed`

**Where Sandboxes sit in the product.** Modal sells three products — Inference, Sandboxes and Training — on one platform, and "All Workspaces are billed monthly." — [pricing page navigation](https://modal.com/pricing) · `pricing-page`; [Billing](https://modal.com/docs/guide/billing) · `docs-confirmed`. ## 2. Isolation technology, and what it actually allows

**Two runtimes, and the current default is a sandboxed container, not a virtual machine.** gVisor is the current default; a KVM-backed VM runtime is opt-in for workloads that need a real kernel, and Modal warns the default may change.

- "Sandboxes run on one of two runtimes" — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "gVisor, a container runtime developed by Google, provides strong isolation and is suitable for most workloads." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "To force continued use of the gVisor runtime, set runtime="gvisor". This is the current default behavior, but the default may change in the future." — [Python SDK release notes](https://modal.com/docs/sdk/py/releases) · `docs-confirmed`
- "VMs run the Sandbox in a virtual machine with its own Linux kernel." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Use the VM runtime for workloads that expect a full Linux environment, such as running Docker inside the Sandbox, mounting FUSE filesystems, or managing resources with nested cgroups." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Switch runtimes via the runtime parameter, or leave unset to let Modal choose for you." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`

**What the boundary buys you.** Modal's security page describes the primitive, and the sandbox page describes the blast radius:

- "Each container runs in its own sandbox, isolated from the host, using primitives like gVisor or microVMs." — [Security and privacy](https://modal.com/docs/guide/security) · `docs-confirmed`
- "Sandboxes are not authorized to access other resources in your Modal workspace the way that Modal Functions are by default." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "a default Sandbox has no ability to accept incoming network connections or access your Modal resources" — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`

**What it permits inside the guest.** More than a jailed process, less than an unconstrained VM.

- Docker is documented, but only on the VM runtime: "Use the VM runtime to run Docker in a Sandbox. Start dockerd as the Sandbox entrypoint and run containers with sb.exec." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- FUSE and nested cgroups are named as VM-runtime reasons. — `inferred` from the runtime description in the [Sandboxes guide](https://modal.com/docs/guide/sandboxes).
- Nested virtualisation is gated: "Nested virtualization is available on the Enterprise plan by setting experimental_options={"enable_nested_virt": True} on a VM Sandbox." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- GPU sandboxes are gVisor-only: "GPU Sandboxes are only supported with runtime="gvisor"." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- You are root, always: "Modal containers always run as root (uid 0)." and "The USER instruction is ignored, whether it appears in your Dockerfile or is inherited from a base image pulled with Image.from_registry." — [Using existing images](https://modal.com/docs/guide/existing-images) · `docs-confirmed`

**Sidecars are a second isolation boundary.** A sandbox can run up to 250 additional containers on the same host, each with the same gVisor-or-VM boundary as a separate sandbox, for keeping credentials or a proxy outside the untrusted container. — [Sandbox sidecars](https://modal.com/docs/guide/sandbox-sidecars) · `docs-confirmed`; "There is a hard limit of **250** concurrent sidecar containers per sandbox" — [same page](https://modal.com/docs/guide/sandbox-sidecars) · `docs-confirmed`.

**Practical reading for a non-specialist** (`inferred` from the quotes above): by default you get *a strongly jailed Linux process tree*, not *a server of your own*. Docker, kernel modules and systemd need the VM runtime; the VM runtime is where it starts to behave like a small computer. Either way, the sandbox cannot reach your other Modal resources unless you give it credentials.

## 3. Lifecycle: every state, what survives, and the timers

**Five events, four of them transient, and no paused or stopped state.** The lifecycle is create → schedule → start → (optionally ready) → finished. There is no state in which compute is held but not billed.

- "Every Sandbox moves through a series of lifecycle events as it progresses from creation to completion." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- The documented events are **Created**, **Scheduled**, **Started**, **Ready** and **Finished**. "Finished — The Sandbox has stopped running." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Once finished, no further commands can be executed inside the Sandbox." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- **No pause exists.** The Python `Sandbox` reference has no pause, suspend, hibernate or resume method; the word pause appears four times in Modal's 2.49 MB documentation corpus and none of them concern sandboxes; battleships records pause/resume as "No". — [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) · `docs-confirmed` for the method list; `not-published` for any pause feature; [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`
- Terminate is destructive: "Terminate sends a SIGKILL, code 137" — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`; "This is a no-op if the Sandbox has already finished running." — [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) · `docs-confirmed`

**The timers.**

| Timer | Value | What it does | Source |
|---|---|---|---|
| Default maximum lifetime | **300 s (5 min)** | Terminates the sandbox | "Sandboxes have a default maximum lifetime of 5 minutes." — [guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |
| Maximum lifetime you can set | **24 h** | Hard ceiling; longer work needs snapshots | "You can change this by passing a timeout of up to 24 hours" — [same](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |
| Idle timeout | **off by default** (`idle_timeout=None`) | Terminates after inactivity | "The amount of time in seconds that a sandbox can be idle before being terminated." — [SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) · `docs-confirmed` |
| Readiness probe | 100 ms interval, 5 min cap | Blocks `wait_until_ready()`, does not terminate | [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |

- "A Sandbox is considered active if any of the following are true" — an active command, writes to stdin, or "an open TCP connection over one of its Tunnels". — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- Idle timeout is a kill switch, not a pause: "Sandboxes can also be automatically terminated after a period of inactivity" — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- The 24-hour ceiling is explicit advice to snapshot: "If you need a Sandbox to run for more than 24 hours, we recommend using Filesystem Snapshots to preserve its state, and then restore from that snapshot with a subsequent Sandbox." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`

**What survives what.**

| Action | Disk | Processes / memory | Identity | Evidence |
|---|---|---|---|---|
| Idle timeout | gone | gone | gone | "automatically terminated" — [guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |
| Lifetime expiry | gone | gone | gone | "maximum lifetime" — [guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |
| `terminate()` | gone | gone | gone | SIGKILL, code 137 — [guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` |
| Filesystem snapshot → new sandbox | copied | no | new sandbox ID | "copies of the Sandbox's root filesystem" — [snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed` |
| Memory snapshot → new sandbox | copied | copied | new sandbox ID | "an exact clone of the original Sandbox" — [snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed` |
| Exit snapshot → new sandbox | copied | no | new sandbox ID | "filesystem snapshot automatically on both graceful and ungraceful Sandbox exits" — [exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed` |

**Exit snapshots are the closest thing to a resume.** Opt in at creation; Modal captures the filesystem on every exit path, including timeouts and OOM.

- "Exit Snapshots take a filesystem snapshot automatically on both graceful and ungraceful Sandbox exits, including terminate(), entrypoint completion, idle timeout, lifetime expiry, and OOM." — [Sandbox exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`
- "Exit snapshot Images are retained for 30 days after creation" — [same page](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`
- "Filesystem only. Exit Snapshots capture the Sandbox filesystem, not memory or directory mounts." — [same page](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`
- "Exit snapshots do not guarantee that a Sandbox's filesystem will be persisted in cases of rare hardware failures." — [same page](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`

**Start time.** Two published figures, both about a second:

- "Containers boot in about one second." — [Cold start performance](https://modal.com/docs/guide/cold-start) · `docs-confirmed`
- "Modal Sandboxes start in under one second." — [Sandboxes product page](https://modal.com/products/sandboxes) · `docs-confirmed`
- **Wake time: not applicable.** With no paused state there is no wake; a restored snapshot is a new sandbox that boots like any other. `inferred` from the absence of pause in the [SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) and the snapshot restore path in [Snapshots](https://modal.com/docs/guide/sandbox-snapshots).

## 4. State tools: snapshots, forks, images, volumes

**Three snapshot types, plus an automatic exit snapshot — and only one captures memory.** All of them produce an Image or snapshot object; none revives the sandbox that was snapshotted. Modal counts "three different kinds of Sandbox snapshots" (filesystem, directory, memory); exit snapshots are a separate feature that produces a filesystem snapshot on exit. — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`

| Tool | Captures | Retention | Restore | Decisive figure |
|---|---|---|---|---|
| Filesystem snapshot | Root filesystem | **30 days** default; configurable; `ttl=None` = indefinite | New sandbox from an Image | 30 days |
| Directory snapshot | One directory | **30 days** default; configurable | Mount into a running sandbox | 30 days |
| Memory snapshot | Disk **and** RAM/processes | **7 days**, not extendable | New sandbox, same instance type | 7 days |
| Exit snapshot (automatic filesystem snapshot) | Root filesystem, on exit | **30 days** | New sandbox from an Image | 30 days |

— [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) and [Exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`

**Filesystem snapshots** are Images, stored as a diff from the base image.

- "Filesystem Snapshots are copies of the Sandbox's root filesystem at a given point in time." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "they are calculated as the difference from your base image, so only modified files are stored" — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "A Filesystem Snapshot only covers the Sandbox's root filesystem. Any mounted Volumes are not covered by this Snapshot" — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Filesystem Snapshots now default to a 30-day TTL." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Both snapshot_filesystem() and snapshot_directory() now accept an explicit TTL parameter that you can use to override the default, including opting out of expiry entirely." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- The SDK default is 30 days and `ttl=None` retains indefinitely: "The resulting Image is retained for ttl seconds (default: 30 days). Pass ttl=None to retain the image indefinitely." — [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) · `docs-confirmed`

**Directory snapshots** capture one path and can be mounted into a sandbox that is already running.

- "Directory Snapshots allow you to snapshot a specific directory within a running Sandbox." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- Mounting replaces whatever is at that path: "If it exists and contains data, the previous directory will be replaced by the mount." — [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) · `docs-confirmed`

**Memory snapshots** are the only ones that preserve running processes, and they are alpha.

- "Sandbox memory snapshots are copies of a Sandbox's entire state, both in memory and on the filesystem." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "These Snapshots can be restored later to create a new Sandbox, which is an exact clone of the original Sandbox." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Memory Snapshots expire 7 days after creation and cannot currently be extended." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Snapshotting a Sandbox will currently cause it to terminate." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Open TCP connections will be closed automatically when a Snapshot is taken" — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Sandboxes created with memory snapshots enabled or restored from Snapshots cannot run with GPUs." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "A Sandbox created with memory snapshots enabled can only be restored on the same exact instance type that the original Sandbox was run on." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "It is not possible to snapshot a Sandbox while an exec command is still running." — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- Re-snapshotting does not reset the clock: "the new snapshot inherits the expiration date of the original snapshot" — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`

**Forking is not a live clone.** Modal has no copy-on-write fork of a running sandbox. Forking in the docs means starting several sandboxes from one filesystem snapshot:

- "Since Filesystem Snapshots are Images, you can create multiple Sandboxes from the same snapshot." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- Each one starts from the captured disk; no memory is copied. `inferred` from the snapshot mechanics above.
- **Live fork: `not-published`.** No fork/clone method appears in the [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox).

**Images** are the template mechanism. A sandbox can boot from a Modal-built Image, a named Image, or an external registry image.

- "Sandboxes support custom images just as Functions do." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "prefer named Images in Sandboxes to ensure they are never built during Sandbox launch" — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "Modal treats external Image tags as immutable once pulled." — [same page](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`

**Volumes** are separate, mountable storage that outlives a sandbox; they are not included in snapshots.

- "Any mounted Volumes are not covered by this Snapshot and will not be included in the resulting Image." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "named Images and Volumes can be used just as with Functions" — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`. They are mounted at creation: `volumes={"/data": modal.Volume.from_name(...)}`.
- "Volumes $0.09 0.09 / GiB / mo" with "includes 1 TiB / mo free" — [pricing page](https://modal.com/pricing) · `pricing-page`. That is **$0.09/GiB-month** after the free terabyte.

**Managing snapshots is manual.** There is no list API, so you must store the IDs yourself.

- "there is currently no API to list all snapshots you have created." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- "Deletion is irreversible. Deleted snapshots cannot be recovered" — [same page](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`
- Snapshot storage has no published price. `not-published` on [pricing](https://modal.com/pricing), [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) and [billing](https://modal.com/docs/guide/billing).

## 5. Machine sizes, GPU, architecture, regions

**There are no fixed sizes.** You request fractional physical cores and MiB of memory; the platform schedules the shape.

- "Each Modal Function or Sandbox container has a default request of 0.125 CPU cores and 128 MiB of memory." — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`
- "The cpu parameter specifies physical CPU cores (1 core = 2 vCPUs), and memory specifies MiB" — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "For both CPU and memory, a maximum is enforced at Function or Sandbox creation time to ensure your containers can be scheduled for execution." — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`
- **The maximum itself is not published.** `not-published`; the docs say a cap exists but give no number. A third-party note cites 64 cores / 336 GB per container, unverified — [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`.

**Bursting is the sizing model.** You are not buying a fixed machine; you set a floor and the sandbox may exceed it.

- "Sandboxes can burst beyond their CPU and memory requests when additional resources are available on the underlying host." — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "Your request guarantees a minimum level of resources, but when spare capacity exists, your Sandbox can use more. You pay for max(request, actual)." — [same page](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "You can set upper limits to cap how much a Sandbox can burst." — [same page](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`

**Disk.** A fixed quota, billed as if it were memory, and not resizable.

- "Sandboxes have the same disk limits as other Modal containers, and their disk size cannot be increased." — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "On the VM runtime, the root filesystem is a fixed 512 GiB." — [same page](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "A per-container disk quota that defaults to 512 GiB." — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`
- "Disk requests are billed by increasing the memory request at a 20:1 ratio." — [same page](https://modal.com/docs/guide/resources) · `docs-confirmed`
- "The maximum disk size is 3.0 TiB" — [same page](https://modal.com/docs/guide/resources) · `docs-confirmed`. **Contradiction:** that sentence is about the `ephemeral_disk` parameter, while the Sandbox page says sandbox disk "cannot be increased". See §14.

**GPU.** The documented NVIDIA types, up to 8 per container, gVisor only, and preemptible.

- "Currently B300, B200, H200, H100, A100, L4, T4 and L40S instances support up to 8 GPUs" — [GPU acceleration](https://modal.com/docs/guide/gpu) · `docs-confirmed`
- "A10 instances support up to 4 GPUs" — [same page](https://modal.com/docs/guide/gpu) · `docs-confirmed`
- "Unlike CPU Sandboxes, GPU Sandboxes are subject to preemption." — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- "GPU Sandboxes are only supported with runtime="gvisor"." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- GPU rates are on the pricing page, from "Nvidia T4 $0.000164" to "Nvidia B300 $0.001972" per second. — [pricing page](https://modal.com/pricing) · `pricing-page`

**Architecture.** `not-published`. Modal's docs do not state a guest CPU architecture, and no ARM option appears in the Sandbox, GPU or region pages. The `uname` example returns `Linux modal 7.2.6` without an architecture. — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed` for the example; `not-published` for the architecture. Do not assume ARM; do not assume x86 from a third party either.

**Regions.** Container placement is selectable; the control plane is not.

- "Sandboxes accept the same region= argument on Sandbox.create" — [Region selection](https://modal.com/docs/guide/region-selection) · `docs-confirmed`

## 6. Networking and secrets

**Inbound is closed by default.** There is no public URL until you ask for a port.

- "a default Sandbox has no ability to accept incoming network connections" — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- Expose a port with `encrypted_ports`, `h2_ports` or `unencrypted_ports`; each gets a tunnel URL, and "you can also expose raw TCP ports to the internet." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "By default, Sandbox tunnels are served from subdomains of w.modal.host." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`

**Two ways to reach an exposed service.**

- **Connect tokens** are the recommended path for HTTP and WebSockets: "You can make authenticated HTTP and WebSocket requests to a Sandbox by generating Sandbox Connect Tokens." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "By default, requests are routed to port 8080 in the container." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- The token becomes a verified header: "The server running on the specified port in the container will receive an authenticated request with an unspoofable X-Verified-User-Data header" — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- **Raw tunnels** are for protocols that authenticate themselves: "While it is recommended to use Sandbox Connect Tokens for HTTP requests and WebSocket connections to the container, you can also expose raw TCP ports to the internet." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "inbound_cidr_allowlist is not enforced on unencrypted tunnels" — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`

**Custom domains** exist but are gated and manually onboarded.

- "Custom domains for Sandbox tunnels are available on the Team and Enterprise plans." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "The infrastructure is production-grade, but onboarding requires a manual setup step." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "Add NS records to your DNS zone pointing to Modal's nameservers." and "Reach out to us on Slack and provide the domain name." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`

**Outbound is open by default, with three restriction levels.**

- "By default, Sandboxes can make outbound connections to any public IP address." — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- Full block: `block_network=True`, which "Drops all outbound traffic." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- CIDR allowlist: `outbound_cidr_allowlist`, "Only allows traffic to the listed CIDR ranges (any protocol)." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- Domain allowlist (beta): `outbound_domain_allowlist`, "Only allows TLS traffic (port 443) to the listed domain names." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- DNS leaks past the allowlists: "Currently, DNS traffic is allowed without restriction except when all outbound traffic is blocked." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- Domain fronting is not prevented: "Many providers reject mismatched requests, but the allowlist itself does not prevent the mismatch." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`
- "You can replace the outbound network policy of a running Sandbox without restarting it." — [same page](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`. Existing connections that the new policy forbids are terminated.

**Static egress IPs** come from Proxies, a Team/Enterprise feature.

- "Proxies are a secure tunnel between Apps and exit nodes with static IPs." — [Proxies](https://modal.com/docs/guide/proxy-ips) · `docs-confirmed`
- "Team Plan users can create one Proxy and Enterprise users three Proxies. Each Proxy can have a maximum of five static IP addresses." — [same page](https://modal.com/docs/guide/proxy-ips) · `docs-confirmed`

**Secrets.** Environment variables are the baseline; the beta outbound policy keeps keys out of the sandbox entirely.

- "You can set environment variables using inline secrets" — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`; the call is `secrets=[modal.Secret.from_dict({...})]`.
- OIDC identity: "Pass include_oidc_identity_token=True to modal.Sandbox.create to inject a MODAL_IDENTITY_TOKEN environment variable containing an OIDC token into the Sandbox." — [Sandboxes guide](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- "This replacement happens outside the Sandbox so the secret never appears in the Sandbox's environment." — [Sandbox secret injection](https://modal.com/docs/guide/sandbox-secret-injection) · `docs-confirmed`
- The outbound policy is beta and immutable per configuration: "An Outbound Policy is an immutable configuration object" — [same page](https://modal.com/docs/guide/sandbox-secret-injection) · `docs-confirmed`

**Egress is metered.** "Starting October 1, 2026, Modal charges for network egress." — [Network egress billing](https://modal.com/docs/guide/network-egress-billing) · `docs-confirmed`

— [Network egress billing](https://modal.com/docs/guide/network-egress-billing) · `docs-confirmed`

**Price while paused: not applicable.** There is no paused state to price. A running sandbox is "billed by the second based on whichever is higher" even when idle; a terminated sandbox bills nothing. — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`; the [Python SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox) has no pause method.

**The unit trap.** Modal calls the CPU unit a physical core and equates it to two vCPUs; the `cpu=` parameter uses that unit. Whether a guest actually sees two CPUs per unit is disputed by measurement (§14). The arithmetic in §11 uses the documented equivalence and then shows the alternative.

**Bursting can cost more than you asked for.** With no cap, the default soft CPU limit is 16 cores above the request, and you pay for what you use.

**Disk is billed as memory.** There is no separate disk rate.

- "Disk requests are billed by increasing the memory request at a 20:1 ratio. For example, requesting 500 GiB of disk will increase the memory request to 25 GiB" — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`

**Region multipliers.** "A multiplier on top of our base usage pricing will be applied to any Function or Sandbox that has a container region defined." — 1.15× for a broad region, 1.75× for a narrow one. — [Region selection](https://modal.com/docs/guide/region-selection) · `docs-confirmed`

**Plans and credits.**

**The model in plain words** (restates the tagged figures; no new claims). You pay by the second for the CPU and memory a sandbox is *using or reserving, whichever is larger*, plus GPU time if any. A sandbox that is running but doing nothing still pays its full request, because there is no pause. Disk is not a separate line: asking for a large disk raises the memory you are billed for. Storage that outlives the sandbox — volumes and snapshots — is billed separately, and snapshot storage has no published rate. Egress is now a line item too, counted across the whole workspace.

**Contradiction to flag.** The pricing page's headline says "You never pay for idle resources — just actual compute time, by the CPU cycle." — [pricing page](https://modal.com/pricing) · `pricing-page`. The Sandboxes section of the same page says "Sandboxes bill max(request, actual) by the second." — [same page](https://modal.com/pricing) · `pricing-page`. For sandboxes, idle time inside the request is billable; the headline is a Functions-shaped statement. See §14.

## 11. Worked cost examples

All figures use the **USD list** rates above: **$0.141912 per core-hour** and **$0.024012 per GiB-hour**, with **1 core = 2 vCPU** as documented. They exclude taxes, egress, snapshot storage, GPU, region multipliers and plan fees unless stated. No minimum billed seconds are assumed beyond the 0.125-core/128-MiB floor.

**The ambiguity that moves every number.** If 2 vCPU really is one `cpu` unit, the shapes below cost what the first table says. If a `cpu` unit is one guest-visible CPU, the same shapes need twice the CPU units and cost 1.6× as much (about 60% more); that is the second table. Modal's docs assert the first; a third-party benchmark reports the second (§14). The guide should show the documented figure and the caveat together.

### (A) 1,000 agent tasks a month, 10 minutes each, 2 vCPU / 4 GiB, deleted after each

**Shape:** 2 vCPU = 1 core at the documented equivalence, 4 GiB memory. 1,000 × 10 min = **166.667 running hours**.

- CPU: 1 × $0.141912 = **$0.141912/h**
- Memory: 4 × $0.024012 = **$0.096048/h**
- Total: **$0.23796/h**
- Per task (1/6 h): **$0.03966**
- 1,000 tasks: **$39.66/month**

| Variant | Hourly | Per task | 1,000 tasks |
|---|---|---|---|
| Documented (1 core = 2 vCPU) | $0.23796 | $0.03966 | **$39.66** |
| Measured (2 cores for 2 vCPU) | $0.379872 | $0.063312 | **$63.31** |
| Documented, EU broad region ×1.15 | $0.273654 | $0.045609 | **$45.61** |
| Starter, after $30 credit | — | — | **$9.66 cash** |
| Team, after $100 credit + $250 fee | — | — | **$189.66 cash** |

Startup is negligible at this shape: 1 second × 1,000 = 0.28 hours, about **$0.07** at the documented rate. No per-task minimum applies beyond the 0.125-core floor, which the 1-core request already exceeds.

### (B) One always-on dev box, 4 vCPU / 8 GiB / 50 GiB disk, 730 h a month

**Shape:** 4 vCPU = 2 cores at the documented equivalence, 8 GiB. 50 GiB of disk is below 20 × 8 GiB = 160 GiB, so it adds nothing to the memory request.

- CPU: 2 × $0.141912 = **$0.283824/h**
- Memory: 8 × $0.024012 = **$0.192096/h**
- Disk: no separate charge
- Total: **$0.47592/h**
- 730 h: **$347.42/month**

| Variant | Hourly | 730 h |
|---|---|---|
| Documented (2 cores for 4 vCPU) | $0.47592 | **$347.42** |
| Measured (4 cores for 4 vCPU) | $0.759744 | **$554.61** |
| Documented, EU broad ×1.15 | $0.547308 | **$399.53** |
| Starter, after $30 credit | — | **$317.42 cash** |
| Team, after $100 credit + $250 fee | — | **$497.42 cash** |

A genuinely always-on box never hits the idle timeout unless one is configured; the default is no idle timeout. But 730 h is **730 sandbox-hours, not one 730-hour sandbox**: the maximum lifetime is 24 h, so an always-on box is at least 31 sandboxes (or a Function-style long-running service). The per-hour price is the same either way. `inferred` from the 24-hour maximum in [Sandboxes](https://modal.com/docs/guide/sandboxes).

### (C) One persistent box, 2 vCPU / 4 GiB / 20 GiB disk, 3 h a day for 30 days, stopped otherwise

**Shape:** 2 vCPU = 1 core, 4 GiB. 20 GiB disk is below 20 × 4 GiB = 80 GiB, so no memory uplift. **Period: 30 days = 720 h, of which 90 h run.** The other 630 h are *not* a stopped state: with no pause, the sandbox is either running or terminated. The cheapest faithful reading is to terminate after each session and recreate the next day, paying nothing between sessions; the snapshot you restore from is separate storage.

Running hours (90):

- CPU: 1 × $0.141912 = $0.141912/h
- Memory: 4 × $0.024012 = $0.096048/h
- Total: **$0.23796/h** × 90 = **$21.42**

Between sessions: **$0** compute, because the sandbox is gone.

| Variant | Running (90 h) | Idle (630 h) | Total |
|---|---|---|---|
| Documented, terminated between sessions | $21.42 | $0 | **$21.42** |
| Measured, terminated between sessions | $34.19 | $0 | **$34.19** |
| Documented, left running 24 h/day | $171.33 | — | **$171.33** |
| Documented, EU broad ×1.15, terminated | $24.63 | $0 | **$24.63** |

The "left running" row is the real trap: without an idle timeout and without an explicit terminate, the sandbox bills 720 h, not 90. `inferred` from the billing basis in [Sandbox resources](https://modal.com/docs/guide/sandbox-resources); the arithmetic is mine.

**What these examples cannot include:** snapshot storage (no published price), egress (workload-dependent, $0.04/GiB over allowance), GPU, Enterprise discounts, and the 1.15×/1.75× region multipliers except where shown. They also assume the task fits the requested shape and does not burst above it; bursting is billed at actual use.

## 12. Same word, different meaning

| Word | What Modal means | What a reader may assume | Consequence |
|---|---|---|---|
| **Snapshot** | Three different objects: filesystem Image, directory Image, memory snapshot. | **Exit snapshot** | An automatic filesystem capture on exit. | A paused sandbox you can resume | It is a new sandbox, filesystem only. — [Exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed` |

## 13. Glossary candidates

- **gVisor** — a container runtime that handles Linux system calls in userspace, so the host kernel is not directly exposed. `inferred` from [Sandboxes](https://modal.com/docs/guide/sandboxes).
- **MicroVM** — a small virtual machine with its own kernel; Modal's VM runtime. `inferred` from [Security](https://modal.com/docs/guide/security).
- **Bursting** — using more CPU or memory than the request when the host has spare capacity, billed at actual use. `inferred` from [Sandbox resources](https://modal.com/docs/guide/sandbox-resources).
- **Filesystem snapshot** — a diff of the root filesystem stored as an Image, with a TTL. `inferred` from [Snapshots](https://modal.com/docs/guide/sandbox-snapshots).
- **Memory snapshot** — disk plus RAM plus running processes, restorable only on the same instance type. `inferred` from [Snapshots](https://modal.com/docs/guide/sandbox-snapshots).
- **Exit snapshot** — an automatic filesystem snapshot taken when a sandbox exits for any reason. `inferred` from [Exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots).
- **Connect token** — a signed URL/token that authenticates an HTTP or WebSocket request to a sandbox port and carries verified user metadata. `inferred` from [Sandbox networking](https://modal.com/docs/guide/sandbox-networking).
- **Tunnel** — the public URL for an exposed sandbox port, encrypted or raw TCP. `inferred` from [Sandbox networking](https://modal.com/docs/guide/sandbox-networking).
- **Sidecar** — an additional container on the same host with its own isolation boundary and image. `inferred` from [Sidecars](https://modal.com/docs/guide/sandbox-sidecars).
- **Outbound policy** — beta header replacement outside the sandbox so a key never enters it. `inferred` from [Secret injection](https://modal.com/docs/guide/sandbox-secret-injection).

## 14. Battleships cross-check, contradictions and gotchas

### Contradictions between Modal's own pages

1. **"You never pay for idle resources" vs sandbox billing.** The pricing headline says "You never pay for idle resources — just actual compute time, by the CPU cycle." — [pricing](https://modal.com/pricing) · `pricing-page`. The Sandboxes section says "Sandboxes bill max(request, actual) by the second." — [same page](https://modal.com/pricing) · `pricing-page`. A sandbox with no active command still bills its request until it is terminated. **`inferred`:** the headline describes scale-to-zero Functions, not sandboxes; the sandbox line is the operative one.
2. **"Disk size cannot be increased" vs "maximum disk size is 3.0 TiB".** Sandbox resources: "their disk size cannot be increased." — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`. Resource guide: "Increased disk sizes can be requested with the ephemeral_disk parameter" and "The maximum disk size is 3.0 TiB". — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`. The second sentence names `@app.function()` only, so the most likely reading is that `ephemeral_disk` is a Function parameter, not a Sandbox one; either way the two pages read as if they disagree. **`inferred`:** treat 512 GiB as the sandbox disk ceiling until Modal confirms otherwise.
3. **"Start in under one second" vs "boot in about one second".** Product page: "Modal Sandboxes start in under one second." — [product](https://modal.com/products/sandboxes) · `docs-confirmed`. Docs: "Containers boot in about one second." — [Cold start](https://modal.com/docs/guide/cold-start) · `docs-confirmed`. Not a contradiction so much as a marketing rounding; plan for ~1 s, not sub-second.
4. **Snapshot without qualification.** The product page markets "Snapshot full or partial filesystems to start large, custom images in under a second." — [product](https://modal.com/products/sandboxes) · `docs-confirmed`. That is the filesystem snapshot. The memory snapshot, which is the one that preserves running processes, "will currently cause it to terminate" and expires in 7 days. — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
5. **"EU data residency" vs US snapshot storage.** Sandboxes can be pinned to `eu` at 1.15×. — [Region selection](https://modal.com/docs/guide/region-selection) · `docs-confirmed`. But "Snapshots you explicitly create" are stored in "United States" regardless of where the workload runs. — [Data residency](https://modal.com/docs/guide/data-residency) · `docs-confirmed`. Pinning the container is not the same as keeping all data in Europe.
6. **Status page 100% vs a 14-minute outage.** The Sandboxes component showed "100% uptime 99.983% uptime 99.989% uptime" across its 30/60/90-day columns, with a "Dashboard and sandbox outage — Down for 14 minutes" dated 16 Sep 2026. — [status.modal.com](https://status.modal.com) · `docs-confirmed`, observed 28 Oct 2026. The 30-day figure simply excludes the older incident; read the 60/90-day columns.

### Discrepancies with battleships.dev

- **CPU unit.** Battleships prices "1 Modal core = 1 vCPU" and reports that `cpu=N` yields a guest with `nproc N`, disputing the docs' "2 vCPU equivalent" reading. — [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`. Modal's docs say the opposite. **`inferred`:** this is the largest single uncertainty in any Modal cost estimate; the guide should show both.
- **Docker inside is listed as No.** Battleships lists "pause/resume, whole disk survives a stop, full VM (own kernel), Docker inside" among its No features for the default card, while documenting a separate VM card. — [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`. Modal documents Docker on the VM runtime: "Use the VM runtime to run Docker in a Sandbox." — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`. Both can be true only if "Docker inside" means "inside the default gVisor runtime". `inferred`.
- **Full VM (own kernel) is listed as No.** The same battleships No list includes "full VM (own kernel)". Same pattern: the VM runtime exists, but it is opt-in and GPU-less. — [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`; [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`.
- **SSH is listed as Yes.** Modal documents `modal shell sb-abc123xyz`, not SSH. — [`modal shell`](https://modal.com/docs/cli/latest/shell) · `docs-confirmed`. `not-published` for an SSH server.
- **Automatic snapshots are listed as No.** Exit snapshots are automatic on exit, opt-in at creation: "Exit Snapshots take a filesystem snapshot automatically on both graceful and ungraceful Sandbox exits" — [Exit snapshots](https://modal.com/docs/guide/sandbox-exit-snapshots) · `docs-confirmed`. The "No" is stale or means "on by default".
- **Fork/clone is listed as Yes.** There is no live fork; there are multiple sandboxes from one snapshot: "you can create multiple Sandboxes from the same snapshot" — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
- **Stale company figures.** Battleships records "Stage: series-c", "Total raised: $466M", and a last round of $355M in May 2026. — [battleships](https://battleships.dev/data/providers/modal.md) · `third-party`. Modal announced a **$750M Series D at $15.75B post-money on 14 Oct 2026** and its company page now says "We've raised over $1.2B". — [Series D post](https://modal.com/blog/1-billion-annualized-run-rate-series-d) · `docs-confirmed`; [company page](https://modal.com/company) · `docs-confirmed`.
- **EU data residency is listed as Yes.** True for container placement, incomplete for snapshots and logs; see contradiction 5.

### Operational gotchas

1. **The default lifetime is five minutes.** "Sandboxes have a default maximum lifetime of 5 minutes." — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`.
2. **There is no pause.** "Snapshotting a Sandbox will currently cause it to terminate." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
3. **Idle is billable.** "billed by the second based on whichever is higher" — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`.
4. **Bursting can raise the bill.** "default soft CPU limit that is set at 16 physical cores above the CPU request" — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`.
5. **Disk is memory.** "Disk requests are billed by increasing the memory request at a 20:1 ratio." — [Configuring CPU, memory, and disk](https://modal.com/docs/guide/resources) · `docs-confirmed`.
6. **Snapshots expire.** "Filesystem Snapshot | 30 days after creation" and "Memory Snapshot | 7 days after creation" — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
7. **Memory snapshots are alpha and picky.** "Sandboxes created with memory snapshots enabled or restored from Snapshots cannot run with GPUs." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
8. **Egress counts private traffic.** "private network traffic sent directly to other Modal containers" — [Network egress billing](https://modal.com/docs/guide/network-egress-billing) · `docs-confirmed`.
9. **Region pinning costs 1.15–1.75×.** "Broad (e.g. us) | 1.15x" and "Narrow (e.g. us-west) | 1.75x" — [Region selection](https://modal.com/docs/guide/region-selection) · `docs-confirmed`.
10. **Starter is small.** "3 workspace seats included" and "100 containers + 10 GPU concurrency" — [pricing](https://modal.com/pricing) · `pricing-page`.
11. **Snapshot storage has no price.** Budget for an unknown, not zero. — `not-published`.
12. **Custom domains are manual.** "onboarding requires a manual setup step" — [Sandbox networking](https://modal.com/docs/guide/sandbox-networking) · `docs-confirmed`.
13. **A sandbox needs an App.** "Sandboxes require an App to be passed when spawned from outside of a Modal container." — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`.
14. **Sidecars share the sandbox's CPU and memory.** "Shares the CPU and memory of the Sandbox" — [Sidecars](https://modal.com/docs/guide/sandbox-sidecars) · `docs-confirmed`.

## 15. Non-technical usability

**Is there a dashboard?** Yes, but it is an operator console, not a builder.

- "The Sandboxes tab on an App page has metrics" — CPU, memory, pressure and exit-reason charts. — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`
- Billing lives in the dashboard: "click on “View invoices” in the “Usage & Billing” section of Settings." — [Billing](https://modal.com/docs/guide/billing) · `docs-confirmed`
- The dashboard's job is to watch and administer sandboxes you or your code created. `inferred` from the documented tabs and metrics.

**Can someone use it without writing code?** Not to create a sandbox.

- Every creation path in the docs is code: "Sandboxes can be created using the Sandbox.create constructor" — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`
- The closest no-code surface is `modal shell sb-abc123xyz`: "Connect to a running Sandbox by ID" — [`modal shell`](https://modal.com/docs/cli/latest/shell) · `docs-confirmed`. It attaches to a sandbox that already exists.
- There is no template gallery, no one-click agent and no app catalogue in the Sandboxes docs. `not-published`.
- **Verdict** (`inferred`): a non-coder can *watch* a sandbox and read its logs, and can *use* a service someone else deployed, but cannot self-serve a first sandbox from the website.

**What does signup take?**

- A payment method: "you must have a payment method on file in order to use Modal." — [Billing](https://modal.com/docs/guide/billing) · `docs-confirmed`
- A workspace; the Starter plan includes "3 workspace seats included". — [pricing](https://modal.com/pricing) · `pricing-page`
- No waitlist is documented for the core product. `not-published` for any waitlist or invite requirement.
- No account was created for this research, so the signup flow itself was not observed. `not-published`.

**Docs and support.**

- Docs are public and machine-readable: there is an [`llms.txt`](https://modal.com/llms.txt) index and an `llms-full.txt` corpus, and "Modal offers official SDKs in Python, Go, and JavaScript/TypeScript, along with a fully-featured CLI". — [docs index](https://modal.com/llms.txt) · `docs-confirmed`
- Support channels: `support@modal.com`, `sales@modal.com`, `security@modal.com`, and a community Slack. — `inferred` from the contact block on the [company page](https://modal.com/company) and the security page's disclosure address.
- Plan-based support: "Access to Modal Community Slack" on Starter and Team; Enterprise adds "Support via private Slack" and "Embedded ML engineering services". — [pricing](https://modal.com/pricing) · `pricing-page`
- No published response-time targets. `not-published`.

**What would trip up a non-engineer**

1. **The first step is Python.** "Sandboxes can be created using the Sandbox.create constructor" — there is no create button. — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`.
2. **The default sandbox dies in five minutes.** "default maximum lifetime of 5 minutes" — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `docs-confirmed`.
3. **Snapshot sounds like save-and-resume.** Only the memory snapshot keeps processes, and "Snapshotting a Sandbox will currently cause it to terminate." — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
4. **An idle sandbox is not free.** "billed by the second based on whichever is higher" — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `docs-confirmed`.
5. **The headline price is per core, not per vCPU.** "Physical core (2 vCPU equivalent)" — [pricing](https://modal.com/pricing) · `pricing-page`.
6. **Region pinning adds 15–75%.** "A multiplier on top of our base usage pricing will be applied" — [Region selection](https://modal.com/docs/guide/region-selection) · `docs-confirmed`.
7. **Snapshots expire silently.** "If you try to use an expired snapshot, Modal will raise a NotFoundError" — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `docs-confirmed`.
8. **There is no status-page SLA link.** Uptime is visible, but "Modal's Service Level Agreement will be attached to the Service Order" — [terms](https://modal.com/legal/terms) · `docs-confirmed`.

## 16. Concept examples

- **Pause** — not available. The nearest equivalent is a memory snapshot, which terminates the source and restores into a new sandbox within 7 days. — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `inferred` from that page.
- **Stop** — `terminate()`, a SIGKILL. The sandbox and its disk are gone. — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `inferred` from that page.
- **Snapshot** — filesystem Image (30 days, configurable), directory Image (30 days), memory snapshot (7 days), or automatic exit snapshot (30 days). — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `inferred` from that page.
- **Fork** — several new sandboxes from one filesystem Image; no live clone. — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `inferred` from that page.
- **Persistent storage** — a Volume mounted at creation, outside the snapshot and outside the sandbox lifecycle. — [Snapshots](https://modal.com/docs/guide/sandbox-snapshots) · `inferred` from that page.
- **Isolation** — gVisor under the current default, KVM VM on request, GPU only on gVisor. — [Sandboxes](https://modal.com/docs/guide/sandboxes) · `inferred` from that page.
- **Billing meter** — allocated CPU and memory per second at `max(request, actual)`, plus GPU seconds. — [Sandbox resources](https://modal.com/docs/guide/sandbox-resources) · `inferred` from that page.
- **Trial** — $30 of compute per month on Starter, not a one-time credit. — [pricing](https://modal.com/pricing) · `inferred` from the pricing page.
- **Secrets** — environment variables, or beta outbound header injection outside the sandbox. — [Secret injection](https://modal.com/docs/guide/sandbox-secret-injection) · `inferred` from that page.
- **Wake** — not applicable; there is no sleeping sandbox. — `inferred` from the absence of pause in [SDK reference](https://modal.com/docs/sdk/py/latest/Sandbox).
